# ترجمه فارسی مستندات CH32V467

## راه‌اندازی اولیه و ساخت

این پوشه شامل نمونه‌های PAC-only و نمونه‌های اولیه مبتنی بر HAL برای میکروکنترلر CH32V467 است. برنامه hal_init قابلیت‌های اولیه HAL شامل کلاک HSI، تقسیم‌کننده‌های گذرگاه، راه‌اندازی کلاک و Reset مربوط به GPIO و مقداردهی اولیه اختیاری درایورهای Embassy را بررسی می‌کند. انتقال سایر درایورهای Peripheral به HAL همچنان ادامه دارد.

نسخه PAC در HAL و نمونه‌ها روی Revision ثابت Git با شناسه e150d53 (تولیدشده از ch32-data با شناسه 844640b و PR شماره 78) قفل شده است. برای ساخت Firmware به Checkout جداگانه PAC یا qingke نیاز نیست؛ وابستگی‌های qingke و qingke-rt از crates.io دریافت می‌شوند.

برای نصب Target و ساخت همه Binaryها، از این دستورات در همین پوشه استفاده کنید:

    rustup target add riscv32imc-unknown-none-elf
    cargo build --release --bins

قطعه پیش‌فرض CH32V467WEU6 است و LEDهای برد به PE8/PE9 متصل‌اند. برای انتخاب RET6 یا VET6 باید دقیقاً یکی از Featureهای ch32v467ret6 یا ch32v467vet6 را همراه no-default-features فعال کنید.

## مراحل اولیه HAL؛ مرحله‌های ۰ و ۱

تا زمان انتشار Metadata اصلاح‌شده V4x7، نسخه PAC در هر دو فایل Cargo ثابت نگه داشته شده است. وابستگی HAL برای هسته V3V به qingke/qingke-rt نسخه 0.8.4 یا جدیدتر نیاز دارد؛ نسخه 0.8.4 نخستین نسخه‌ای است که اصلاح mstatus.MPIE در critical-section را دارد.

اجرای hal_init در سه حالت زیر امکان‌پذیر است:

    cargo run --release --bin hal_init --features hal
    cargo run --release --bin hal_init --features hal,clock-dividers
    cargo run --release --bin hal_init --features embassy

این برنامه یک‌بار ch32_hal::init() را فراخوانی می‌کند، Cache کلاک RCC، وضعیت HSI، فعال‌بودن کلاک GPIO/AFIO و نتیجه rcc::refresh(None) را بررسی می‌کند. سپس HAL_INIT_RESULT=PASS را از طریق RTT گزارش می‌دهد و Heartbeat را تکرار می‌کند. با clock-dividers فرکانس‌های SYSCLK/HCLK/PCLK1/PCLK2 به‌ترتیب 20/10/2.5/5 MHz هستند؛ در حالت عادی هر چهار کلاک 20 MHz هستند. برنامه خروجی GPIO ندارد. مقدار HAL_INIT_RESULT برابر 0 پیش از ورود، 1 هنگام بررسی، 2 در موفقیت و 3 در شکست است.

نسخه Blocking از تأخیر HAL مبتنی بر SysTick استفاده می‌کند. در حالت embassy، پیکربندی SysTick بررسی و Heartbeat با حلقه چرخشی CPU تولید می‌شود؛ اعتبارسنجی Executor، دقت Timer، سرریز شمارنده و خواب/بیداری به مرحله 3 مربوط است. هنگامی که Embassy مالک SysTick است، از Delay مسدودکننده استفاده نکنید.

Featureهای پیش‌فرض HAL در این نمونه غیرفعال‌اند؛ برای فعال‌سازی GPIO EXTI باید Feature با نام exti انتخاب شود. درایورهای زمان مبتنی بر TIM تا زمان انتقال به V4x7 این تراشه را نمی‌پذیرند. DMA و سایر درایورهای انتقال‌نیافته نیز در دسترس نیستند. پیکربندی HSE/PLL پیاده‌سازی نشده و refresh منابع کلاک مذکور را رد می‌کند.

## مرحله ۲ HAL: GPIO و EXTI

برای ساخت محلی بدون پروگرام‌کردن برد:

    cargo build --release --bin hal_blinky --features hal
    cargo build --release --bin hal_exti --features exti

نمونه hal_blinky با خروجی‌های GPIO کتابخانه HAL، پایه‌های PE8 و PE9 را با تأخیر Blocking اسمی 100 میلی‌ثانیه متناوب می‌کند. پس از هر تغییر، Output Latch و سطح خوانده‌شده از پایه بررسی می‌شوند. پس از 20 تغییر، GPIO_OUT_RESULT=PASS گزارش می‌شود. نماد Debugger پیش از شروع 0، هنگام اجرا 1، در موفقیت 2 و در شکست 3 است. با embassy به‌جای Delay از حلقه چرخشی CPU استفاده می‌شود؛ چشمک‌زدن مبتنی بر Executor در hal_embassy قرار دارد. خواندن خروجی روی WEU6 موفق بوده و تناوب LEDهای PE8/PE9 در 2026-11-04 به‌صورت دیداری تأیید شده است؛ دقت شکل موج هنوز به ابزار اندازه‌گیری نیاز دارد.

برای hal_exti، پایه PA0 را با سه شاخه سیم به PB1، PB8 و PC13 متصل کنید تا هر چهار پایه یک شبکه سیگنال مشترک تشکیل دهند. پیش از اجرا مطمئن شوید پایه‌ها در دسترس‌اند و مدار دیگری آن‌ها را درایو نمی‌کند. برنامه ابتدا PA0 را شناور می‌کند و Pull-up/Pull-down هر ورودی را جداگانه می‌آزماید؛ سپس حالت شناور را بین آزمون‌ها بازمی‌گرداند. در ادامه PA0 را درایو کرده و هم‌زمان منتظر تغییر هر سه ورودی می‌ماند. مسیرهای EXTI1، EXTI9_5، EXTI15_10 و مسیریابی GPIO پورت‌های B و C پوشش داده می‌شوند. هشت دور آزمون، لبه‌های بالارونده/پایین‌رونده/هر دو لبه، Callback واقعی بیدارسازی IRQ، لغو Future، پاک‌شدن Pending قدیمی و مسلح‌سازی مجدد را بررسی می‌کنند. انتظار برای هر لبه Timeout محدود دارد.

این نمونه Futureها را مستقیماً Poll می‌کند و از Executor یا Timer استفاده نمی‌کند. نتیجه GPIO_EXTI_RESULT=PASS از RTT گزارش می‌شود؛ نماد Debugger برای قبل از ورود/در حال اجرا/موفق/ناموفق به‌ترتیب 0/1/2/3 است. در صورت شکست، برنامه متوقف می‌شود. نبود جامپر نیز می‌تواند آزمون Pull یا مسیریابی اولیه را ناموفق کند. پذیرش سخت‌افزاری این بخش هنوز انجام نشده است؛ ساخت موفق برنامه، رفتار الکتریکی یا تحویل وقفه را اثبات نمی‌کند.

پس از آماده‌سازی سیم‌کشی، برای پروگرام و اجرا از دستورات زیر استفاده کنید:

    cargo run --release --bin hal_blinky --features hal
    cargo run --release --bin hal_exti --features exti

فیلدهای Remap تفکیک‌شده USART1 در PCFR1 bit 2 و PCFR2 bit 26 پیاده‌سازی شده و با آزمون‌های محلی مدل رجیستر پوشش داده شده‌اند؛ انتقال واقعی USART در مرحله بعدی قرار دارد.

## مرحله ۳ HAL: زمان‌بندی Embassy

نمونه hal_embassy مالکیت SysTick را در اختیار می‌گیرد، شمارنده 32 بیتی را پیش از ایجاد Timerهای برنامه نزدیک سرریز قرار می‌دهد و یکنواختی زمان را بررسی می‌کند. سپس سه Task با Timerهای 100، 150 و 230 میلی‌ثانیه‌ای را اجرا می‌کند که هرکدام 16 بار تکرار می‌شوند. دو Task پایه‌های PE8/PE9 را کنترل می‌کنند. آزمون، Alarmها در دو سوی سرریز، Deadlineهای لغوشده و گذشته، Deadlineهای کوتاه و هشت مرتبه انتظار WFI با وقفه‌های Mask‌شده را بررسی می‌کند. نتیجه EMBASSY_RESULT=PASS از RTT گزارش می‌شود و پس از آن Heartbeat مبتنی بر Timer ادامه می‌یابد. نماد نتیجه 0/1/2/3 به‌ترتیب به معنی اجرا‌نشده/درحال اجرا/موفق/ناموفق است. نزدیک‌کردن شمارنده به سرریز فقط برای آزمون است؛ برنامه کاربردی نباید شمارنده زمان در حال اجرا را Reset یا بازنویسی کند.

در V4x7 رجیسترهای CNT و CMP هر دو 32 بیتی هستند و کلمات رزروشده در آدرس‌های 0x0c و 0x14 قرار دارند. PAC ثابت‌شده دیگر نماهای High-word یا 64 بیتی غیرواقعی را ارائه نمی‌کند. درایور اختصاصی شمارنده را به‌صورت نرم‌افزاری توسعه می‌دهد و حتی در نبود Timer کاربر، وقفه‌های نگهداری را فعال نگه می‌دارد. وقفه‌ها نباید به‌اندازه نصف دوره سرریز (حدود 859 ثانیه با کلاک پیش‌فرض) Mask بمانند. تبدیل زمان، نسبت‌های غیرصحیح شمارنده به Tick را در HCLKهای 20 و 10 MHz پشتیبانی می‌کند.

هر دو پیکربندی کلاک در 2026-11-01 روی WEU6، از جمله بیدارسازی IRQ و WFI، موفق شدند. فاصله Heartbeat مشاهده‌شده روی میزبان تقریباً یک ثانیه بود؛ دقت کالیبره‌شده نوسان‌ساز و جریان مصرفی در حالت خواب اندازه‌گیری نشده‌اند. اعتبارسنجی ورودی GPIO و EXTI خارجی تا زمان آماده‌شدن سیم‌کشی به تعویق افتاده است.

Target استاندارد RV32IMC در .cargo/config.toml با ویژگی‌های xwchc، zve64x، zvl64b و zvbb توسعه داده شده است. ABI از نوع ILP32 با ممیز شناور نرم‌افزاری باقی می‌ماند و CAS بومی فعال نمی‌شود. این ویژگی‌های برداری با پروژه WCH در مسیر EVT/EXAM/CPU/AccuracyDelayInTick/AccuracyDelayInTick.wvproj از SDK مربوط به CH32V407/CH32V467 مطابقت دارند. باید از زیرمجموعه برداری صحیحِ تعبیه‌شده استفاده شود، نه +v؛ زیرا +v قابلیت‌های برداری ممیز شناور و حداقل VLEN برابر 128 بیت را نیز القا می‌کند. این برد VLEN = 64 bits و نبود افزونه اسکالر F را گزارش می‌کند.

نسخه Rust nightly با شماره 1.101.0-nightly، تاریخ 2026-10-17 و LLVM 23.1.4 هشدار می‌دهد که xwchc یک ویژگی ناشناخته/ناپایدار Target در Rust است، اما آن را به LLVM منتقل می‌کند. ویژگی معماری ELF شامل xwchc2p2 است و Disassembly و آزمون برد اثرگذاری آن را تأیید می‌کنند. نسخه‌های آینده rustc ممکن است این Flag را رد کنند؛ برای تکرار آزمون، این Toolchain را نگه دارید. xwchc از طریق cfg(target_feature) در Rust قابل مشاهده نیست؛ بنابراین نمونه ISA ویژگی‌های برداری را هنگام کامپایل بررسی می‌کند و دستورهای فشرده WCH را در زمان اجرا می‌آزماید.

بسته qingke-rt نسخه 0.8.4 از crates.io راه‌اندازی هسته V3V را از طریق qingke-rt/v3v فراهم می‌کند و PAC نیز Vectorها و چیدمان حافظه دستگاه را ارائه می‌دهد. Linker memory map سفارشی نگهداری نمی‌شود. تقسیم پیش‌فرض PAC با نام c512_r200 شامل 512 KiB حافظه Flash اصلی و 200 KiB SRAM است و 480 KiB Flash دیگر پس از آن قرار دارد. اسکریپت Linker تولیدشده نواحی Flash را در یک Boot alias به اندازه 992 KiB در آدرس 0x00000000 ادغام می‌کند؛ انتهای Stack در 0x20032000 است. تقسیم‌بندی Option Byte تراشه باید با این چیدمان مطابقت داشته باشد؛ Option Byteها را بدون بررسی تغییر ندهید.

## نمونه‌ها و نحوه مشاهده خروجی

- blinky: LEDهای برد روی PE8/PE9 با فاصله اسمی 100 میلی‌ثانیه (فرکانس 5 Hz برای هر LED) متناوب می‌شوند. تنظیم کلاک و هر Heartbeat از طریق defmt RTT گزارش می‌شود، نه SDI. پایه‌های PE8/PE9 خروجی Push-pull با فرکانس تنظیمی 2 MHz و سطح‌های مخالف هستند.
- rtt: خروجی GPIO ندارد؛ پیش از راه‌اندازی کلاک گزارش می‌دهد و اطلاعات کلاک/Heartbeat را تقریباً هر ثانیه تکرار می‌کند. جایگزین نمونه قدیمی sdi_print شده است.
- cpuid: خروجی GPIO ندارد؛ پس از پنجره 500 میلی‌ثانیه‌ای برای اتصال، گزارش یک‌باره شناسه CPU را از طریق defmt RTT چاپ می‌کند. مواردی مانند mvendorid، marchid، mimpid، mhartid، misa، مقادیر خام Hex، وجود CSR، فیلدهای هویتی WCH، XLEN و بیت‌های افزونه ISA (از جمله F/V) را شامل می‌شود. خواندن غیرمجاز CSR هنگام Probe با present=false گزارش می‌شود؛ Exceptionهای نامرتبط باعث توقف می‌شوند. مقدار صفر به معنی نبود CSR تلقی نمی‌شود. فیلدهای Decodeشده پکیج را مشخص نمی‌کنند و بیت‌های اعلام‌شده ISA، رفتار واقعی دستورها یا ایمنی Atomicها را اثبات نمی‌کنند. نمونه فقط CSRها را می‌خواند؛ qingke-rt/v3v هنگام راه‌اندازی وضعیت برداری را فعال می‌کند (mstatus.VS = Dirty). گزارش تکرار نمی‌شود و برای گزارش مجدد باید برنامه را دوباره اجرا یا Reset کنید.
- isa: دستورهای Load/Store فشرده WCH برای Byte و Halfword را آزمایش می‌کند و در کنار آن توابع مستقل Rust برای کپی Volatile جهت بررسی Disassembly دارد. دستورهای vsetvli، بارگذاری برداری، vadd.vv، Store و دستور Zvbb vror.vi را برای عناصر 8/16/32/64 بیتی می‌آزماید. هر حالت 19 عنصر را در قطعه‌های با طول متغیر پردازش و تمام نتایج را با جمع و چرخش Scalar به‌صورت Wrapping مقایسه می‌کند؛ Overflow و عناصر انتهایی نیز پوشش داده می‌شوند. خطاها و Trapهای هم‌زمان از طریق RTT ثبت می‌شوند. ISA_RESULT پیش از آزمون 0، هنگام اجرا 1، در موفقیت 2 و در شکست/Trap برابر 3 است. خروجی GPIO ندارد.
- همه نمونه‌ها نمادهای ELF با نام BOOT_STAGE (مقدار 1 یعنی ورود به Init و 2 یعنی پیکربندی کلاک/SysTick) و HEARTBEAT را برای مشاهده از Debugger و بدون Console ارائه می‌کنند.

فایل defmt.x فراداده Log را نگه می‌دارد، defmt-rtt نماد _SEGGER_RTT را در RAM فراهم می‌کند و qingke/critical-section-impl دسترسی Logger تک‌هسته‌ای را Serialize می‌کند. RTT به آدرس‌های SDI یعنی DATA0/DATA1 وابسته نیست. گزینه disable-blocking-mode باعث می‌شود با قطع اتصال میزبان، اجرای برنامه ادامه یابد؛ پرشدن Buffer می‌تواند موجب از دست‌رفتن Log شود. Panic handler همچنان panic-halt است؛ بنابراین Panicهای Rust بدون متن خطا پردازنده را متوقف می‌کنند.

## Runner مربوط به probe-rs و پشتیبانی محلی V4x7

Runner پیش‌فرض probe-rs run --chip CH32V467WEU6 است و DEFMT_LOG=info را به‌صورت پیش‌فرض دارد. cargo build به‌تنهایی عملیات Flash انجام نمی‌دهد.

نسخه محلی Checkout در مسیر ../../../probe-rs اکنون خانواده WCH-Link با شناسه 0xA6 را می‌شناسد و فایل CH32V4X7_Series.yaml را شامل می‌شود: شش پکیج V407/V467 با RAM برابر 200 یا 136 KiB، به‌همراه الگوریتم‌های Flash تولیدشده برای V4x7. نسخه محلی با cargo install --path probe-rs-tools --bin probe-rs --force --locked نصب شده است؛ ابزار نصب‌شده در ~/.cargo/bin همان نسخه‌ای است که Runner پیش‌فرض Cargo از PATH پیدا می‌کند.

برای انتخاب صریح نسخه Checkout، متغیر CARGO_TARGET_RISCV32IMC_UNKNOWN_NONE_ELF_RUNNER را به مسیر باینری محلی probe-rs تنظیم کنید. دستورهای cargo run برای blinky، rtt، cpuid و isa، Firmware را Flash و اجرا می‌کنند؛ دستور probe-rs attach برای اتصال به ELF منطبقِ از قبل پروگرام‌شده، بدون Flash یا Reset استفاده می‌شود.

بررسی‌های سخت‌افزاری فقط‌خواندنی در 2026-10-28 با Binary نسخه Release محلی موفق بودند: info --verbose --protocol jtag خانواده 0xA6 و Chip ID برابر 0x46740011 را گزارش می‌کند. خواندن با انتخاب صریح Chip همین شناسه و مقدار USER در آدرس 0x1FFFF802 برابر 0xBF را تأیید می‌کند که نشان‌دهنده RAM برابر 200 KiB و منطبق با چیدمان پیش‌فرض Linker است. اگر --chip حذف شود، WEU6 شناسایی می‌شود اما اتصال بعدی از طریق USB Timeout می‌شود؛ بنابراین Chip را صریحاً انتخاب کنید. پروگرام Flash و RTT زنده در 2026-10-31 موفق بودند. خروجی دیداری نمونه PAC-only با نام blinky هنوز تأیید نشده است؛ تناوب LED در hal_blinky در 2026-11-04 تأیید شده است. V4x7 در مسیر خودکار Unprotect هنگام اتصال WCH-Link فعال نشده است.

## وضعیت برد پس از بازیابی (2026-11-03)

Firmware قبلی با HCLK پایین باعث شده بود Probe با خطای 81 55 01 01 متصل نشود. دستور wlink erase --method power-off --chip CH32V4X7 برد را بدون دست‌کاری Option Byteها بازیابی کرد. پس از بازیابی، نمونه‌های پشتیبانی‌شده دوباره اجرا شدند؛ EXTI و حالت سرریز طبیعی در این دور اجرا نشدند. نتایج حساس به زمان با Flash کردن (probe-rs download)، Reset و خواندن Markerهای RAM پس از اجرا جمع‌آوری شدند؛ زیرا اتصال زنده RTT/Debugger هسته را متوقف می‌کند.

- نمونه‌های PAC-only شامل isa، cpuid، rtt و نمونه‌های HAL شامل hal_init، hal_blinky، hal_rcc (با 9 پیکربندی HSI و 14 پیکربندی HSE)، hal_embassy، hal_time_scale (حالت پیش‌فرض، PLL و AHB/512) و hal_systick_stress (512 سرریز با کلاک پیش‌فرض و تقسیم‌شده؛ کنترل منفی با نتیجه مورد انتظار FAIL code=13) موفق شدند.

- hal_eth در 2026-11-04 آزمون Echo فریم خام و Throughput TCP را با موفقیت گذراند (شناسه PHY برابر 0x73719011). نمونه hal_sdio نبود پاسخ کارت را به‌درستی گزارش کرد. hal_usbhs (Echo از طریق CDC روی USBHS1) در 2026-11-04 در برابر میزبان macOS موفق شد.
- دو اشکال درایور شناسایی و اصلاح شدند: SPI::blocking_flush درحالی‌که SPE=0 بود منتظر TXE می‌ماند و نخستین نوشتن hal_spi قفل می‌شد؛ همچنین برنامه‌نویسی سریع Page به‌جای WRBSY منتظر BSY|WRBSY بود و flash-write-test را با Timeout مواجه می‌کرد. هر دو مورد در آزمون‌های روی برد hal_spi و hal_flash --flash-write-test پوشش داده شده‌اند.

تناوب LEDهای PE8/PE9 در hal_blinky در تاریخ 2026-11-04 به‌صورت دیداری تأیید شده است. مواردی که هنوز به سخت‌افزار یا تجهیزات نیاز دارند: سرریز طبیعی 32 بیتی SysTick، سیم‌کشی ورودی GPIO/EXTI، Loopback سیمی USART/SPI، EEPROM خارجی I2C، تجهیزات جانبی خارجی I3C/CAN/SD، بررسی تقسیم RAM در Option Byte، اندازه‌گیری فرکانس HSI و اندازه‌گیری‌های آنالوگ.

SDI روی برد کاربر کار نکرده است؛ عدم تطابق آدرس یا Handshake فقط یک فرضیه است و علت قطعی تشخیص داده نشده. نمونه‌های فعلی دیگر به رجیسترهای SDI دسترسی ندارند. نمونه‌های PAC-only صراحتاً HSI 20 MHz و HCLK /1 را انتخاب می‌کنند و از SysTick به‌صورت Polling استفاده می‌کنند. به کریستال خارجی نیاز ندارند، PLL/PSRAM را پیکربندی نمی‌کنند و وقفه Peripheralها را فعال نمی‌کنند. زمان‌بندی‌ها اسمی هستند و تا زمان اندازه‌گیری روی سخت‌افزار، از جمله اثر سربار Log، دقت قطعی ندارند.

## USBHS؛ دستگاه و Echo از طریق CDC

نمونه USBHS چهار حالت ساخت برای USBHS1، کلاک PLL، کلاک HSE و USBHS2 دارد. در حالت پیش‌فرض USBHS1 از PA12 به‌عنوان D+ و PA11 به‌عنوان D− استفاده می‌کند. گزینه usbhs2 رابط USBHS2 را انتخاب می‌کند: PB7 = D+ و PB6 = D−؛ این رابط روی VET6/WEU6 موجود است و در RET6 در دسترس نیست. کانکتور داده USB متناظر و زمین مشترک را متصل کنید. اتصال Debug مربوط به WCH-Link، اتصال USB Host به این پایه‌ها را فراهم نمی‌کند. هر دو رابط را به یک زوج سیم مشترک متصل نکنید. USBHS2 از وقفه، Bus gate و UTMI gate مستقل خود استفاده می‌کند.

این نمونه از USB Full-speed با بسته‌های Bulk از نوع CDC و اندازه 64 بایت استفاده می‌کند. HSI، PLL مشترک 480 MHz مربوط به USBHS را تغذیه می‌کند؛ گزینه clock-pll علاوه بر آن HCLK را روی 200 MHz قرار می‌دهد. گزینه clock-hse به کریستال 25 MHz نیاز دارد و PLL مربوط به USBHS را از HSE تغذیه می‌کند. حالت HSI تاکنون Enumeration و Echo را با موفقیت گذرانده است؛ پایداری بلندمدت و دقت فرکانس هنوز باید آزمایش شوند. VID/PID نمایشی برابر c0de:cafe است و شناسه تخصیص‌یافته برای محصول نهایی محسوب نمی‌شود.

پس از Enumeration، پورت CDC را با فعال‌بودن DTR باز کنید. اسکریپت Linux وابستگی جانبی ندارد و Payloadهای باینری 1 تا 4096 بایتی را بررسی می‌کند؛ مرزهای 63/64/65 بایت و همه مقادیر ممکن Byte نیز پوشش داده می‌شوند. انتقال در هر دو جهت به‌صورت هم‌زمان انجام می‌شود و اختلاف داده، قطع اتصال یا Timeout باعث شکست آزمون خواهد شد. با ده دور پیش‌فرض انتظار می‌رود نتیجه PASS: 120 exchanges, 62160 bytes matched باشد. Firmware پس از یک بسته کامل 64 بایتی، یک ZLP در جهت IN اضافه می‌کند تا Echoهایی که اندازه‌شان دقیقاً مضرب بسته است بدون انتظار برای بسته بعدی تحویل داده شوند.

در 2026-11-04، USBHS1 روی میزبان macOS با آدرس /dev/tty.usbmodemV4_USBHS11 شناسایی شد و Echo انجام داد؛ آزمون پیش‌فرض ده‌دوری نتیجه PASS: 120 exchanges, 62160 bytes matched را گزارش کرد. USBHS2، حالت‌های کلاک PLL/HSE، Bus Reset، اتصال مجدد کابل و عملکرد High-speed هنوز روی سخت‌افزار آزمایش نشده‌اند.

نماد USBHS_STAGE برابر 1 هنگام راه‌اندازی، 2 هنگام انتظار برای اتصال CDC، 3 پس از اتصال و 4 پس از Echo داده است. متغیرهای USBHS_ECHO_PACKETS، USBHS_ECHO_BYTES و USBHS_ERRORS به‌ترتیب تعداد بسته‌ها/بایت‌های موفق و خطاهای سرریز Buffer را ثبت می‌کنند. رسیدن به Stage 4 به‌تنهایی به معنی موفقیت کامل نیست؛ داده برگشتی میزبان را مقایسه کنید، Bus Reset و بستن/بازکردن مجدد پورت و اتصال دوباره کابل را بیازمایید و مطمئن شوید شمارنده خطا صفر باقی می‌ماند.

درایور برای طول عمر Bus و Endpointها از SRAM داخلی با هم‌ترازی مناسب استفاده می‌کند. Endpoint صفر 64 بایت رزرو می‌کند و هر جهت غیرکنترلی Buffer بسته مستقل خود را تخصیص می‌دهد. Endpointهای فیزیکی 1 تا 7 در دسترس‌اند؛ جهت‌های جفت‌شده IN/OUT باید حداکثر اندازه بسته یکسان داشته باشند، زیرا سخت‌افزار رجیستر طول را مشترک استفاده می‌کند. لغو نوشتن IN ممکن است بسته متعلق به آن را در صف باقی بگذارد؛ نوشتن بعدی پیش از کپی داده جدید منتظر آن بسته می‌ماند. Reset، غیرفعال‌سازی و دریافت SETUP کنترلی جدید، Transferهای معلق را نامعتبر می‌کنند. درایور حذف VBUS را تشخیص نمی‌دهد؛ بنابراین جداشدن فیزیکی کابل فعلاً رویداد PowerRemoved تولید نمی‌کند.

نمونه CDC عمداً از Full-speed استفاده می‌کند. PHY پرسرعت، زمان‌بندی Isochronous، Remote wakeup و بازگشت به Full-speed به آزمون سخت‌افزاری نیاز دارند. Embassy USB نسخه 0.6، Descriptor پیکربندی Other-speed ارائه نمی‌کند؛ بنابراین تغییر صرف سرعت درایور برای ساخت دستگاه کامل دو‌سرعته کافی نیست. Aliasهای Endpoint از 9 تا 15، حالت Burst، قابلیت LPM و حالت USB Host هنوز پیاده‌سازی نشده‌اند.

مدل رجیستر میزبان در زمان توسعه تخصیص بسته را با 27 بررسی پوشش داده بود؛ این مدل حذف شده و نمونه روی برد جایگزین آن شده است. ماتریس 16 حالته کتابخانه و شش پیکربندی ساخت نمونه CDC موفق بوده‌اند و Enumeration و Echo مربوط به USBHS1 نیز در 2026-11-04 روی برد موفق شده‌اند؛ سایر موارد سخت‌افزاری همچنان نیازمند آزمون‌اند.

## آزمون تنش سرریز SysTick

این آزمون از TIM2 به‌عنوان شمارنده مرجع و Watchdog استفاده می‌کند و به سیم‌کشی ورودی نیاز ندارد. هر اجرا 512 سرریز شتاب‌داده‌شده SysTick را بررسی می‌کند؛ مدیریت عادی وقفه با Maskکردن وقفه‌ها به‌مدت 50/500/2000 میکروثانیه در دو سوی مرز سرریز جایگزین می‌شود. آزمون بررسی می‌کند ISR پیش از اجازه‌دادن به کد اصلی برای خواندن دوباره زمان Embassy، رجیستر CMP را دوباره مسلح کرده باشد؛ بنابراین خواندن Foreground نمی‌تواند سرریز ازدست‌رفته را پنهان کند. Epoch نرم‌افزاری، Deadlineها و اندازه‌گیری زمان نسبی دوثانیه‌ای نیز بررسی می‌شوند.

سه اجرای مستقل برای هر پیکربندی کلاک، تمام 3072 سرریز را با موفقیت گذراندند. زمان انتظار اندازه‌گیری‌شده برای تأخیر 3 ms در HCLK برابر 20 MHz، بین 3036 تا 3098 میکروثانیه و در HCLK برابر 10 MHz بین 3076 تا 3152 میکروثانیه بود. این اعداد شامل تأخیر ISR/Executor و نمونه‌های مشاهده‌شده‌اند، نه کران بدترین حالت. TIM2 و SysTick هر دو از HSI استفاده می‌کنند؛ بنابراین این آزمون دقت نوسان‌ساز را کالیبره نمی‌کند. سرریز طبیعی 32 بیتی و Mask طولانی وقفه‌ها آزمون‌های جداگانه‌اند. حالت clock-pll,stress-natural-wrap یک دوره کامل سرریز طبیعی را در HCLK برابر 200 MHz (حدود 172 ثانیه) اضافه می‌کند؛ این آزمون ساخته شده اما هنوز روی سخت‌افزار با موفقیت اجرا نشده است.

برای کنترل منفی، Feature با نام stress-disable-systick-irq را اضافه کنید؛ Watchdog باید FAIL code=13 گزارش کند. پس از آن دوباره یک پیکربندی عادی را Flash کنید. در نبود اتصال پیوسته RTT، متغیر SYSTICK_STRESS_RESULT را بررسی کنید (1 در حال اجرا، 2 موفق و 10 تا 18 ناموفق)؛ SYSTICK_STRESS_STATS شامل تعداد دورها، حداقل/حداکثر زمان انتظار، زمان سپری‌شده TIM2 و زمان Embassy بر حسب میکروثانیه است. پنج ثانیه پس از Reset صبر کنید و سپس برای خواندن نتیجه متصل شوید. اتصال پیوسته Debugger می‌تواند تأخیر بسیار بیشتری ایجاد کند یا دوره‌های کوتاه مرجع TIM2 را از دست بدهد؛ مرجع از دوره کامل 65.536 ms شمارنده استفاده می‌کند تا این خطر کمتر شود.

نمونه hal_time_scale تبدیل مقادیر متوقف‌شده شمارنده سخت‌افزاری را با مرجع عددصحیح گسترده بررسی می‌کند. برای HCLK برابر 200 MHz گزینه clock-pll و برای AHB /512 گزینه clock-slow را اضافه کنید. حالت دوم فرکانس کسری SysTick دارد؛ درایور نسبت منبع/تقسیم‌کننده را حفظ می‌کند و آن را به Hz گرد نمی‌کند. نمونه پس از بررسی، HSI /1 را بازمی‌گرداند تا Debugger بتواند دوباره متصل شود. پس از بازیابی 2026-11-03، حالت پیش‌فرض، PLL و AHB/512 روی سخت‌افزار موفق شدند؛ hal_systick_stress نیز با کلاک پیش‌فرض و تقسیم‌شده (هرکدام 512 سرریز) و کنترل منفی stress-disable-systick-irq با نتیجه FAIL code=13 موفق بود. حالت stress-natural-wrap با مدت حدود 172 ثانیه هنوز اجرا نشده است.

## بررسی مهاجرت DMA

نمونه hal_dma تمام 13 کانال DMA1 و 11 کانال DMA2، از جمله هر دو پنجره رجیستر، را آزمایش می‌کند. 216 کپی با عرض‌های Byte/Halfword/Word انجام می‌دهد، طول‌های Byte برابر 1/2/3/31/256/65535 و Guardهای Buffer را بررسی می‌کند؛ سپس یک انتقال بدون درخواست Peripheral را لغو و همان کانال را دوباره استفاده می‌کند. هر کپی Timeout دوثانیه‌ای دارد. سیم‌کشی سیگنال لازم نیست. Bufferهای بزرگ حدود 133 kB از RAM مصرف می‌کنند؛ برای این نمونه چیدمان پیش‌فرض SRAM برابر 200 KiB را حفظ کنید.

DMA_RESULT برابر 1 در حال اجرا، 2 موفق، 10 Timeout، 11 عدم تطابق محتوا، 12 خرابی Guard و 13 درخواست غیرمنتظره Peripheral است. DMA_CASES، DMA_CHANNELS_PASSED و DMA_LAST (اندیس کانال، تعداد Word و اندازه Byte هر Word) نیز برای بررسی ارائه شده‌اند. Handler خطای انتقال سخت‌افزاری، کانال را متوقف و Panic می‌کند؛ خطای قابل‌بازیابی از Transfer بازگردانده نمی‌شود.

Link کردن Release و 13 آزمون میزبان موفق بوده‌اند؛ این آزمون‌ها پنجره‌های رجیستر و ماشین حالت Transfer را با رجیسترهای PAC متصل به RAM پوشش می‌دهند. سپس hal_dma در 2026-11-03 روی سخت‌افزار موفق شد (24 کانال و 216 کپی). حاشیه زمانی وقفه‌ها به‌صورت مستقل اندازه‌گیری نشده است.

## بررسی مهاجرت USART

نمونه hal_usart پایه‌های TX پیش‌فرض هر ده نمونه USART را درایو می‌کند. برای این حالت سیم‌کشی ورودی لازم نیست. زمان‌بندی ارسال Blocking و رجیستر BRR، نوشتن Asynchronous با DMA، وقفه‌های TC، لغو Write/Flush و استفاده مجدد پس از لغو بررسی می‌شوند. نرخ‌های Baud برابر 9600، 115200 و کمینه 1 Mbps یا PCLK/16 هستند. USART1 از PCLK2 و سایر نمونه‌ها از PCLK1 استفاده می‌کنند.

| USART | پایه‌های TX / RX | کانال‌های DMA مربوط به TX / RX |
| --- | --- | --- |
| 1 | PA9 / PA10 | DMA1_CH4 / DMA1_CH5 |
| 2 | PA2 / PA3 | DMA1_CH7 / DMA1_CH6 |
| 3 | PB10 / PB11 | DMA1_CH2 / DMA1_CH3 |
| 4 | PC10 / PC11 | DMA2_CH5 / DMA2_CH3 |
| 5 | PC12 / PD2 | DMA2_CH4 / DMA2_CH2 |
| 6 | PC0 / PC1 | DMA2_CH6 / DMA2_CH7 |
| 7 | PC2 / PC3 | DMA2_CH8 / DMA2_CH9 |
| 8 | PC4 / PC5 | DMA2_CH10 / DMA2_CH11 |
| 9 | PB1 / PB2 | DMA1_CH8 / DMA1_CH9 |
| 10 | PE0 / PE1 | DMA1_CH10 / DMA1_CH11 |

برای V4x7، سازنده‌های Async فقط TX باید Binding وقفه USART را پیش از کانال DMA به‌صورت صریح دریافت کنند؛ این کار تضمین می‌کند flush().await با وقفه TC بیدار شود. نوشتن Buffer خالی موفق است؛ Bufferهای طولانی‌تر از 65535 بایت خطای Error::BufferTooLong برمی‌گردانند. خطاهای Transfer مربوط به DMA از سیاست Panic درایور پیروی می‌کنند.

پس از فراهم‌شدن سیم‌کشی ورودی، PA9 را به PA10 متصل و Feature با نام usart-loopback را همراه embassy فعال کنید تا آزمون RX در USART1 اضافه شود. این آزمون اختیاری، Transferهای کامل تکراری، طول‌های IDLE، لغو/شروع مجدد دریافت و ادامه فعالیت TX پس از Drop کردن نیمه RX جداشده را بررسی می‌کند. تابع check_rx_mappings فقط تمام ترکیب‌های پایه/DMA مربوط به RX را از نظر Type بررسی می‌کند و آزمون بردی انجام نمی‌دهد.

برای بررسی زمان‌بندی، با انتخاب صریح --chip CH32V467WEU6 Flash کنید، Reset کنید و دست‌کم ده ثانیه اجرای مستقل را پیش از اتصال برای خواندن RAM صبر کنید. دسترسی پیوسته RTT/Debug می‌تواند پنجره‌های کوتاه لغو را تغییر دهد. USART_RESULT (1 در حال اجرا، 2 موفق، 10 تا 22 خطای TX و 30 تا 37 خطای Loopback)، USART_CHANNELS_PASSED و USART_SNAPSHOTS (فرکانس PCLK، مقدار BRR، رجیسترهای CTLR1 و CTLR3) را بررسی کنید.

هر چهار حالت ساخت، از جمله PLL به‌همراه APB Divider و Loopback، با موفقیت Link شده‌اند. هجده آزمون میزبان پیکربندی UART و حالت Asynchronous را همراه آزمون‌های موجود DMA پوشش می‌دهند. این نتایج شکل موج فیزیکی TX یا صحت RX را اثبات نمی‌کنند. آزمون TX پیش‌فرض در 2026-11-03 روی سخت‌افزار برای هر 10 کانال موفق شد؛ این آزمون دریافت را بررسی نمی‌کند و Timer آن از کلاک سیستم استفاده می‌کند. RX و Loopback همچنان به اتصال PA9–PA10 نیاز دارند.

## گام‌های بعدی

1. پوشش سخت‌افزاری الگوریتم‌های Flash تولیدشده برای V4x7 را گسترش دهید (دوام و بدترین زمان Erase) و Timeout اتصال مجدد در Auto-detection را بررسی کنید؛ تا آن زمان از --chip صریح استفاده کنید.
2. تقسیم RAM در Option Byte را تأیید و فرکانس HSI را اندازه‌گیری کنید. V4x7 خروجی MCO روی PA8 دارد؛ مقدار RCC_CFGR0.MCO[3:0] = 0b0101 منبع HSI را انتخاب می‌کند. HAL اکنون rcc::Mco::new(p.PA8, McoSource::HSI) را ارائه می‌دهد (نمونه hal_mco)، اما هنوز روی سخت‌افزار تأیید نشده است.
3. آزمون‌های باقی‌مانده وابسته به سیم‌کشی یا تجهیزات جانبی را اجرا کنید: Loopback USART، Loopback SPI، EEPROM روی I2C، هدف خارجی I3C/CAN/SD/Ethernet و سرریز طبیعی SysTick. آزمون‌های Regression مربوط به Time-driver، DMA و USART پیش‌فرض در 2026-11-03 موفق شده‌اند؛ 9 پیکربندی کلاک مبتنی بر HSI و 14 پیکربندی دارای HSE در RCC نیز موفق بوده‌اند. خروجی HAL و Timerهای Embassy/سرریز/WFI در آزمون‌های مرحله 2 و 3 موفق بوده‌اند. آزمون ورودی GPIO و EXTI خارجی تا زمان آماده‌شدن سیم‌کشی معلق است.

ساخت این نمونه‌ها فقط کامپایل و Link شدن را اعتبارسنجی می‌کند و به معنی تأیید راه‌اندازی سخت‌افزاری یا پشتیبانی کامل Peripheralها نیست.

## اعتبارسنجی سخت‌افزاری (2026-10-31)

روی برد متصل CH32V467WEU6، نمونه isa با ویژگی‌های Target پیکربندی‌شده Flash و اجرا شد. RTT نتیجه mstatus=0x80001e88، VS=3 و VLEN=64 bits را گزارش کرد. آزمون Load/Store بایتی و Halfword فشرده Xwchc و کپی‌های Rust موفق بود. آزمون‌های Zve64x vadd و Zvbb vror برای عناصر 8، 16، 32 و 64 بیتی، هرکدام با 19 عنصر و تعداد Chunkهای 3، 5، 10 و 19 موفق شدند و ISA RESULT: PASS ثبت شد.

دستور llvm-readelf-21 -A روی فایل اجرایی isa ویژگی معماری zve64x1p0_zvkb1p0_zvl32b1p0_zvl64b1p0_xwchc2p2 را در کنار سایر ویژگی‌های به‌ارث‌رسیده تأیید می‌کند. برای بررسی تولید کد از llvm-objdump-21 با ویژگی‌های xwchc، zve64x، zvl64b و zvbb استفاده کنید. LLVM 21 دستورهای فشرده WCH را با Mnemonicهای معمول lbu، sb و sh نمایش می‌دهد؛ Encoding دو‌بایتی آن‌ها را متمایز می‌کند. تابع isa_copy_byte شامل 218c برای Load و a10c برای Store است؛ isa_copy_halfword شامل a10e برای Store است. Assembly صریح نیز lhu فشرده را اجرا می‌کند. این بررسی‌ها فقط دستورهای اجراشده را اعتبارسنجی می‌کنند و همه دستورهای هر افزونه، Vectorization خودکار، Context switching برداری یا صحت Atomicها را اثبات نمی‌کنند.

## اعتبارسنجی HAL I2C

در زمان توسعه از مدل میزبان I2C/DMA برای رویدادهای Bus و تکمیل DMA استفاده شده بود، اما این مدل حذف شده است؛ نمونه روی برد و آزمون‌های hal_spi و hal_flash --flash-write-test برای دو اشکال مرزی اصلاح‌شده در 2026-11-03 جایگزین آن هستند.

نمونه hal_i2c نگاشت پیش‌فرض PB6/PB7 و Remap پایه‌های PB8/PB9 را در فرکانس 100 kHz و هر دو نسبت Duty در 400 kHz بررسی می‌کند. برای حالت کلاک بالا و APB Prescaler، Featureهای clock-pll و clock-dividers را اضافه کنید.

اجرای پیش‌فرض Probeهای فقط آدرس در 0x55 انجام می‌دهد و پاک‌سازی پس از Cancel را بررسی می‌کند. I2C_PROBES مقدار 0 برای ACK، مقدار 1 برای NACK و مقدار 2 برای Timeout را ثبت می‌کند. Timeout روی پایه‌های بدون سیم‌کشی، ارتباط را اعتبارسنجی نمی‌کند. I2C_RESULT=2 فقط آزمون‌های پیکربندی و پاک‌سازی را تأیید می‌کند؛ مقادیر 10 تا 30 نشان‌دهنده خطا هستند. Snapshot رجیسترهای زمان‌بندی در I2C_SNAPSHOTS قرار دارد.

برای اعتبارسنجی با دستگاه خارجی، یک EEPROM از نوع 24C02 با تغذیه 3.3V و آدرس 0x50 متصل کنید: SCL=PB6، SDA=PB7، زمین مشترک و Pull-up خارجی مناسب. سپس Feature با نام i2c-eeprom را اضافه کنید. این آزمون مقدار مبنا را می‌خواند و خواندن Blocking و Async DMA، دنباله‌های 1/2/3 بایتی، Bufferهای مجاور، Repeated START و Cancel/استفاده مجدد را مقایسه می‌کند. فقط Pointer آدرس EEPROM نوشته می‌شود و داده غیرفرار تغییر نمی‌کند. برای بررسی زمان‌بندی الکتریکی و ACK، خطوط SCL/SDA را با اسیلوسکوپ یا Logic Analyzer اندازه‌گیری کنید.

هر دو حالت ساخته و Link شده‌اند. پیکربندی پیش‌فرض در 2026-11-03 آزمون Probe آدرس و پاک‌سازی را روی سخت‌افزار با موفقیت گذراند؛ آزمون دستگاه خارجی با i2c-eeprom هنوز انجام نشده است.

## اعتبارسنجی Timer/PWM در HAL

نمونه hal_timer هر هشت Timer را در فرکانس‌های 50، 1000 و 10000 Hz با استفاده از Update Interrupt و پنجره زمانی Embassy آزمایش می‌کند. برای بررسی هر دو دامنه کلاک Timer مربوط به APB پس از Prescaling، Featureهای clock-pll و clock-dividers را اضافه کنید. این آزمون همچنین هر شش Timer مربوط به PWM را در حالت‌های شمارش صعودی، نزولی و Center-aligned پیکربندی و مقادیر Duty برابر 0%، 50% و 100% را در رجیستر بررسی می‌کند.

پس از آن TIM1 پایه‌های PE9/PE8 را به‌ترتیب به‌عنوان CH1/CH1N با Full remap، فرکانس 1 kHz و Duty برابر 50% درایو می‌کند؛ Dead-time درخواستی 20 Tick از کلاک ورودی Timer است. برای بررسی فرکانس، قطبیت و Dead-time هر دو خروجی را با اسیلوسکوپ مشاهده کنید. خواندن رجیستر به‌تنهایی رفتار الکتریکی را اثبات نمی‌کند.

## اعتبارسنجی SPI در HAL

نمونه hal_spi در حالت پیش‌فرض به سیم‌کشی ورودی نیاز ندارد. داده از SPI1 روی PA5/PA7، از SPI2 روی PB13/PB15 و از SPI3 روی PB3/PB5 ارسال می‌شود. هر نمونه هر چهار Mode، هر دو Bit order، نوشتن Blocking و DMA در عرض 8/16 بیت، تغییر فرکانس و Cancel همراه با استفاده مجدد را بررسی می‌کند. SPI_RESULT، SPI_CASES (در پایان 24) و SPI_SNAPSHOTS شامل Control، Status و فرکانس واقعی را بررسی کنید. این آزمون عملکرد فرستنده و وضعیت Peripheral را می‌سنجد؛ دریافت داده به Loopback فیزیکی یا دستگاه جانبی نیاز دارد.

برای Feature با نام spi-loopback، پایه SPI1 PA7 (MOSI) را به PA6 (MISO) متصل کنید. آزمون انتقال Blocking بایتی و DMA از نوع Halfword، طول‌های نابرابر Buffer و خواندن Dummy را در تمام Modeها و هر دو Bit order مقایسه می‌کند. تکمیل هر دو سازنده Receive-only نیز بررسی می‌شود؛ در این سازنده‌ها MOSI قطع است و مقادیر دریافتی عمداً بررسی نمی‌شوند. SPI_LOOPBACK_RESULT برای حالت Skip برابر 0، در حال اجرا 1 و در موفقیت 2 است. نمونه پایه CS را مدیریت نمی‌کند؛ هنگام آزمون Loopback یک دستگاه خارجی را در حالت Select نگه ندارید.

هر دو پیکربندی Build و Link می‌شوند. hal_spi در 2026-11-03، پس از اصلاح blocking_flush، 24 حالت پیکربندی و چرخه عمر را روی سخت‌افزار با موفقیت گذراند. اشکال قبلی این بود که TXE در حالی Poll می‌شد که SPE=0 بود و اولین نوشتن قفل می‌شد. آزمون‌های Loopback اختیاری‌اند و به اتصال MOSI–MISO نیاز دارند. آزمون‌های مدل رجیستر میزبان، Cancel، بیدارسازی خطای IRQ، Flush و پیکربندی Dummy شانزده‌بیتی را پوشش می‌دهند؛ اما زمان‌بندی سیگنال فیزیکی یا صحت داده واقعی DMA را اثبات نمی‌کنند.

## اعتبارسنجی DAC و RNG در HAL

نمونه hal_dac از PA4/PA5 استفاده می‌کند و به سیم‌کشی ورودی نیاز ندارد. مقدارخوانی دیجیتال DOR برای قالب‌های 8 بیتی و هر دو قالب 12 بیتی، Trigger نرم‌افزاری دوگانه، طول عمر جداگانه کانال‌ها، انتقال DMA با Trigger تایمر TIM6 از طریق DMA2_CH3/CH4، Cancel در حالت Circular، استفاده مجدد و تغییرات موج مثلثی را مقایسه می‌کند. DAC_RESULT، DAC_CASES، DAC_SNAPSHOTS و DAC_WAVE_RANGE را بررسی کنید. تکمیل DMA کانال را فعال باقی می‌گذارد تا مقدار نهایی Holding Register در Trigger بعدی به خروجی برسد؛ آزمون پیش از بررسی دو دوره Trigger اضافی صبر می‌کند. مقادیر Scalar با چینش Left-aligned، نمونه‌های 12 بیتی بدون شیفت هستند؛ اما Bufferهای DMA در حالت Left-aligned نمونه را به بیت‌های 15:4 منتقل می‌کنند. برای تعیین دقت آنالوگ خروجی، PA4 و PA5 را جداگانه اندازه‌گیری کنید.

نمونه hal_rng تعداد 32 کلمه، یک Buffer سی‌ویک‌بایتی و پاک‌سازی وقفه و Drop/Create مجدد را بررسی می‌کند. RNG_RESULT، RNG_SAMPLES و RNG_SOURCE_HZ را بررسی کنید. خواندن تک‌Poll که Drop شده ممکن است روی سخت‌افزار واقعی پیش از Cancel کامل شود؛ لغو قطعی حالت Pending در مدل رویداد میزبان پوشش داده شده است. این آزمون کیفیت Entropy را ارزیابی نمی‌کند. Feature با نام rng-usbhs-pll منبع PLL برابر 480 MHz مربوط به USBHS را انتخاب می‌کند؛ در غیر این صورت RNG از SYSCLK استفاده می‌کند و این انتخاب مستقل از AHB divider است. مالتی‌پلکسر PLL با I2S مشترک است. مقداردهی اولیه RNG منتظر Entropy نمی‌ماند و APIهای Fallible خطای Seed یا Clock را گزارش می‌کنند؛ APIهای غیرقابل‌خطای rand_core در صورت خطای سخت‌افزار Panic می‌کنند.

پیکربندی‌های پیش‌فرض و PLL ساخته و Link می‌شوند. مجموعه آزمون میزبان، طول عمر DAC/لغو DMA و خطا/بیدارسازی/لغو RNG را پوشش می‌دهد. هر دو نمونه در 2026-11-03 آزمون‌های روی برد را با موفقیت گذراندند.

## بررسی مهاجرت ADC

نمونه پیش‌فرض به سیم‌کشی نیاز ندارد. خواندن Vref و دمای ADC1، خواندن هم‌زمان ADC1/ADC2 از طریق وقفه مشترک ADC1_2، اسکن DMA مربوط به Vref/دما در ADC1 روی DMA1_CH12، DMA مربوط به ADC2 PA0 روی DMA1_CH13، لغو/استفاده مجدد و طول عمر مستقل کلاک بررسی می‌شوند. PA0 می‌تواند شناور باشد؛ نتیجه آن فقط مسیر دیجیتال را بررسی می‌کند و دقت آنالوگ را اعتبارسنجی نمی‌کند. ADC_SAMPLES شامل چهار خواندن اولیه و سپس 32 فریم اسکن درهم‌آمیخته Vref/دما است.

ADC_RESULT هنگام اجرا 1، در موفقیت 2 و در شکست 10 تا 23 است. ADC_CLOCK_HZ فرکانس ADC kernel را ثبت می‌کند. ADC_CANCEL_PENDING نشان می‌دهد آیا آزمون Cancel واقعاً یک انتقال Pending را مشاهده کرده است یا خیر. خواندن‌های Async دارای Timeout برابر 500 ms هستند؛ Cancel ناشی از Timeout، تبدیل و DMA را متوقف می‌کند.

کلاک ADC در RCC می‌تواند HCLK یا USBHS PLL با تقسیم 1 تا 32 را انتخاب کند. هر دو مسیر از APB2 prescaler و ADC prescaler با مقادیر 2/4/6/8 نیز عبور می‌کنند و با محاسبه کلاک EVT مطابقت دارند. درایور حد 30 MHz برای کلاک، حد تبدیل 2 MS/s و زمان نمونه‌برداری توصیه‌شده 17.1 us برای حسگر دما را اعتبارسنجی می‌کند. در فرکانس 30 MHz، زمان نمونه‌برداری حداقل 2.5 سیکل انتخاب شود. نمونه PLL از APB2 /2 استفاده می‌کند تا طولانی‌ترین زمان نمونه‌برداری برای حسگر دما کافی باشد. ولتاژ مرجع داخلی اسمی 1.2 V است؛ نمونه ادعای ولتاژ یا دمای کالیبره‌شده کارخانه‌ای ندارد.

برای Loopback آنالوگ اختیاری، PA4 را به PA0 متصل و Feature با نام adc-loopback را اضافه کنید. این آزمون خروجی‌های DAC برابر 512، 2048 و 3584 را با ADC1 مقایسه می‌کند و خطای 100 Count را مجاز می‌داند. بدون این اتصال آن را فعال نکنید. مشخصه‌یابی دقیق آنالوگ همچنان به مرجع خارجی و تجهیزات اندازه‌گیری نیاز دارد.

درایور فعلاً تبدیل Regular مستقل را پشتیبانی می‌کند؛ گروه‌های Injected، حالت‌های Dual-ADC، Watchdog و APIهای Trigger سخت‌افزاری در کارهای آینده قرار دارند. آزمون‌های رجیستر/رویداد میزبان و Buildها موفق‌اند. نمونه در 2026-11-03 آزمون‌های دیجیتال روی برد را گذراند؛ Loopback آنالوگ PA4–PA0 اختیاری سیم‌کشی نشده بود.

## بررسی مهاجرت Flash

حالت پیش‌فرض نمونه hal_flash فقط Flash را می‌خواند و محدوده‌های نامعتبر و درخواست‌های خالی را بررسی می‌کند. متغیرهای FLASH_RESULT، FLASH_SNAPSHOTS، FLASH_TEST_RANGE و FLASH_TEST_CASES نتیجه را ثبت می‌کنند. در این حالت هیچ فرمان Erase یا Program صادر نمی‌شود.

برای آزمون ذخیره‌سازی مخرب و صریح، Feature با نام flash-write-test را فعال کنید. این آزمون محتوای موجود در 32 KiB انتهایی Flash، یعنی بازه 0x080F0000 تا 0x080F8000، را پاک می‌کند. گزینه memory-split-usr را فعال و این ناحیه را با flash-test.x رزرو می‌کند؛ ELF دارای Reservation از نوع NOLOAD و بدون Byteهای Download است. کد در Flash با Zero-wait باقی می‌ماند. برنامه‌های سفارشی نیز باید طبق RM اطمینان دهند توابع Erase/Program و توابع فراخوانی‌شده از آن‌ها از Flash با Zero-wait اجرا شوند.

V4x7 برنامه‌نویسی سریع 256 بایتی، Program استاندارد 16 بیتی، Erase سکتور 4 KiB و Erase سریع Block برابر 32 KiB را پشتیبانی می‌کند. Halfwordهای خام در حالت Erased مقدار 0xE339 می‌خوانند. بنابراین درایور خام فقط ReadNorFlash را پیاده‌سازی می‌کند. تابع into_nor_flash(from, to) یک Partition داده صریح ایجاد می‌کند که با Encoding مبتنی بر XOR، بایت‌های Erased را به 0xFF نرمال می‌کند و امکان رعایت قرارداد NorFlash را می‌دهد. این نمایش Byteهای ذخیره‌شده را تغییر می‌دهد و برای Firmware image مناسب نیست. پیش از Program مجدد Erase کنید؛ درایور تضمین چندبارنوشتن ارائه نمی‌دهد و تاریخچه Program فیزیکی را نگه نمی‌دارد.

آزمون اختیاری هر دو اندازه Erase، هر دو حالت Program، Buffer مبدأ غیرهم‌تراز، بررسی Readback، رد Program تکراری و Partition کدگذاری‌شده را بررسی می‌کند. Snapshotهای Protection و Clock را بدون تغییر Option Byte، Protection یا تخصیص RAM/Code بررسی می‌کند. هنگام هر عملیات فیزیکی وقفه‌ها Mask می‌شوند؛ Datasheet برای Erase یک Block تا 200 ms زمان مجاز می‌داند. Timeout در حالت Busy رجیسترهای کنترلر را دست‌کاری نمی‌کند؛ درایور را نگه دارید و پس از Idle شدن سخت‌افزار یک‌بار recover() را دوباره امتحان کنید. Config::poll_limit تعداد Poll رجیستر است، نه زمان سپری‌شده.

مجموعه آزمون میزبان شامل 104 آزمون موفق است و ماتریس 16 پیکربندی کتابخانه نیز موفق شده است. Buildهای Read-only، Write-test و Embassy/PLL با فرکانس 200 MHz با موفقیت Link می‌شوند. بررسی ELF ناحیه رزروشده و Entry pointهای Zero-wait را تأیید می‌کند. مسیرهای Read-only و flash-write-test در 2026-11-03 روی سخت‌افزار موفق شدند؛ این پس از اصلاح انتظار Busy در برنامه‌نویسی سریع Page بود. دوام و بدترین زمان Erase هنوز آزمایش نشده‌اند.

## بررسی مهاجرت CAN

نمونه hal_can از CAN1 در حالت SilentLoopback روی PA11/PA12 استفاده می‌کند؛ بنابراین به Transceiver یا سیم‌کشی نیاز ندارد. ابتدا Loopback مسدودکننده را در 125/500/1000 kbit/s بررسی می‌کند، سپس 72 فریم Data/Remote استاندارد و Extended با طول Payload از 0 تا 8 را آزمایش می‌کند. Filterهای دقیق، فریم‌های استاندارد را از طریق Bankهای 0 و 13 به FIFO0 و فریم‌های Extended را به FIFO1 هدایت می‌کنند. شناسه‌های ردشده، Bankهای نامعتبر Filter، دریافت Pending لغوشده، استفاده مجدد، گزارش FIFO overrun و آزادسازی کلاک هنگام Drop درایور نیز بررسی می‌شوند.

CAN_RESULT هنگام اجرا 1، در موفقیت 2 و در شکست 10 تا 26 است. CAN_FRAMES تعداد فریم‌های Standard Data، Extended Data، Standard Remote و Extended Remote را می‌شمارد. CAN_SNAPSHOTS شامل PCLK1، BTIMR، فعال‌سازی Filter، تخصیص FIFO، فعال‌سازی وقفه و وضعیت خطا است.

API اختصاصی V4x7 هر دو FIFO دریافت، هر 14 بانک Filter و Filterهای List/Mask با عرض 16/32 بیت را پشتیبانی می‌کند. Filter::exact قالب شناسه و در صورت درخواست RTR را تطبیق می‌دهد؛ Filter::registers نمایش رجیستر RM را برای چیدمان‌های دیگر ارائه می‌کند. انتخاب Bitrate به نسبت دقیق کلاک نیاز دارد و از هر ده بیت Prescaler استفاده می‌کند. محدوده TS1/TS2/SJW استاندارد از EVT پیروی می‌کند؛ Extended long-TS1، حالت Time-triggered و CAN FD فعال نیستند. این تراشه Classical CAN 2.0A/B را پیاده‌سازی می‌کند.

ارسال Blocking و Async هر دو منتظر نتیجه تکمیل می‌مانند. try_transmit غیرمسدودکننده فقط فریم را Submit می‌کند و Mailbox را برمی‌گرداند؛ نتیجه آن تا زمان استفاده مجدد از Mailbox یا Drop کنترلر معتبر است. فریم‌های Pending هرگز جایگزین نمی‌شوند. Traitهای Blocking/nb در embedded-can از FIFO0 دریافت می‌کنند؛ متدهای دریافت صریح، FIFO را انتخاب می‌کنند. در صورت نیاز عملیات Async را در with_timeout قرار دهید. Config::poll_limit در حالت Blocking تعداد Poll رجیستر را می‌شمارد، نه زمان را. لغو ارسال فقط درخواست Mailbox متعلق به همان Future را Abort می‌کند و نمی‌تواند فریمی را که قبلاً روی Bus ارسال شده پس بگیرد. Cancel دریافت، منابع وقفه آن را غیرفعال می‌کند. Overrun از دست‌رفتن داده را گزارش می‌دهد، اما فریم‌های صف‌شده همچنان قابل خواندن‌اند.

مجموعه آزمون میزبان شامل 128 آزمون موفق است و فریم/زمان‌بندی/Filter CAN و چرخه عمر کنترلر/وقفه/لغو را بررسی می‌کند. تمام 16 پیکربندی کتابخانه موفق‌اند و هر دو پیکربندی نمونه Build و Link می‌شوند. Loopback داخلی 72 فریمی در 2026-11-03 روی سخت‌افزار موفق شد. زمان‌بندی واقعی Bus، Arbitration، Transceiverها و کیفیت الکتریکی به راه‌اندازی CAN خارجی نیاز دارند.

## اعتبارسنجی SDIO در HAL

برای نمونه hal_sdio از سوکت SD با تغذیه 3.3 V و زمین مشترک استفاده کنید. CK به PC12، CMD به PD2 و D0 به PC8 متصل می‌شود. حالت چهار‌بیتی از PC9/D1، PC10/D2 و PC11/D3 نیز استفاده می‌کند. گزینه sdio-remap، D0/D1 را به PB14/PB15 منتقل می‌کند؛ CK، CMD و D2/D3 ثابت می‌مانند. خطوط CMD و Data به Pull-up خارجی مطابق طراحی کارت/سوکت نیاز دارند. درایور کانال DMA2 شماره 4 را در اختیار می‌گیرد. سیم‌کشی ورودی GPIO برای این آزمون لازم نیست.

نمونه فقط خواندن انجام می‌دهد: کارت را مقداردهی اولیه می‌کند، SD Status و Block صفر را می‌خواند، خواندن Blocking و Async را مقایسه می‌کند، خواندن دو Block را با خواندن‌های تکی مقایسه می‌کند و اگر خواندن Async در Poll نخست همچنان Pending باشد آن را لغو می‌کند. پس از Cancel، خاموش‌شدن DMA را بررسی کرده، دوباره مقداردهی اولیه می‌کند و Block صفر را تکرار می‌کند. هیچ داده‌ای روی کارت نوشته نمی‌شود. نبود پاسخ کارت جدا از موفقیت آزمون خواندن گزارش می‌شود.

HSI پیش‌فرض HCLK برابر 20 MHz فراهم می‌کند. فقط برای این نمونه، clock-pll، HCLK را روی 100 MHz (AHB /4) قرار می‌دهد؛ Divider هشت‌بیتی SDIO در HCLK برابر 200 MHz نمی‌تواند کلاک Identification را تولید کند. درایور این پیکربندی را با BadClock رد می‌کند. clock-dividers فقط کلاک‌های APB را تغییر می‌دهد تا منبع Kernel از HCLK بررسی شود. کلاک انتقال درخواستی یک حد بالاست: در حالت پیش‌فرض 25 MHz و با sdio-high-speed برابر 50 MHz، مشروط به قابلیت کارت و Divider موجود. sdio-bypass امکان Bypass همراه با کنترل جریان سخت‌افزاری را فراهم می‌کند و پیش‌فرض غیرفعال است.

SDIO_RESULT هنگام اجرا 1، برای نبود پاسخ کارت 2، برای آزمون خواندن موفق 3 و برای شکست 10 تا 26 است. SDIO_CARD_INFO شامل دو کلمه پایین/بالای تعداد Block، کلاک انتقال بر حسب Hz، RCA و انتخاب High-speed است. SDIO_FIRST_BYTES شامل 64 بایت اول Block صفر و SDIO_CANCELLED نشان‌دهنده اجرای مسیر Cancel است. نمونه در 2026-11-03 روی سخت‌افزار اجرا شد و با نبود کارت، SDIO_RESULT=2 را گزارش کرد؛ این نتیجه در نبود کارت مورد انتظار بود. خواندن واقعی کارت، High-speed و مسیر Cancel هنوز آزمایش نشده‌اند.

## اعتبارسنجی Ethernet در HAL

این نمونه به کریستال HSE با فرکانس 25 MHz نیاز دارد و ETH PLL را فعال می‌کند. HCLK پیش‌فرض 20 MHz است؛ clock-pll آن را روی 200 MHz می‌گذارد و clock-dividers فقط کلاک‌های APB را تغییر می‌دهد. درایور از PHY یکپارچه 10/100M و پایه‌های تفاضلی اختصاصی، همراه با جک و مدار Magnetics برد استفاده می‌کند. اتصال خارجی RMII GPIO لازم نیست. LEDهای GPIO اختیاری PHY غیرفعال‌اند تا PE8/PE9 برای نمونه‌های دیگر آزاد بمانند. آدرس MAC محلی نمونه 02:00:00:00:00:47 است؛ هنگام استفاده هم‌زمان چند برد در یک شبکه، آدرس یکتا انتخاب کنید.

درایور Trait مربوط به embassy-net-driver را با Checksum نرم‌افزاری و منابع DMA ثابت پیاده‌سازی می‌کند. این نمونه فریم خام را بدون پیکربندی IP آزمایش می‌کند. روی یک میزبان Linux متصل به شبکه Ethernet برد، اسکریپت eth_echo_test.py را با رابط سیمی اجرا کنید؛ اسکریپت به دسترسی root یا CAP_NET_RAW نیاز دارد. 100 Echo را در طول‌های Payload برابر 46/47/128/512/1500 بایت با بررسی Sequence و داده هر فریم اعتبارسنجی می‌کند. نمونه فقط فریم‌های EtherType برابر 0x88b5 را که به MAC خودش آدرس‌دهی شده و پیشوند CH32V4-ECHO دارند Echo می‌کند. در macOS باید از Peer مبتنی بر BPF استفاده شود؛ eth_echo_test.py به AF_PACKET لینوکس وابسته است.

در 2026-11-04 نمونه از میزبان macOS و مبدل USB Ethernet با سرعت 100 Mbit/s و Full-duplex، تعداد 25 Echo (پنج دور از طول‌های 46/47/128/512/1500 بایت) را با موفقیت گذراند. ETH_STATS تعداد 115 فریم دریافت‌شده، 25 Echo و بدون خطای TX، RX یا DMA را گزارش کرد.

ETH_RESULT برابر 1 هنگام ورود به Init، 2 پس از مقداردهی اولیه بدون Link، 3 هنگام برقراری Link، 4 پس از صف‌کردن Echo، 10 در خطای Init و 11 در خطای زمان اجرا است. مقدار 4 به‌تنهایی تحویل فریم را اثبات نمی‌کند؛ اسکریپت Peer باید فریم برگشتی را بررسی کند. ETH_PHY_ID شناسه PHY و ETH_STATS تعداد فریم‌های دریافتی، Echoهای صف‌شده، خطاهای TX/RX و خطاهای DMA را ثبت می‌کنند. برای نخستین بررسی شناسایی PHY، کابل لازم نیست. از 2026-11-03 شناسه PHY برابر 0x73719011 گزارش شده است.

پیاده‌سازی از نقشه رجیستر DMA کاهش‌یافته RM و وقفه PHY در بیت 11 پیروی می‌کند. تغییر Link، MAC را بدون Poll کردن DMASR[22:17] دوباره پیکربندی می‌کند؛ این تراشه در آن قسمت مقدار Idle مستندنشده 110 گزارش می‌کند که پیش‌تر باعث Timeout در انتظار اولین Link-up شده بود. جزئیات FES access و Fatal bus-error bit 13 بین RM و EVT تعارض دارند. مذاکره 100M Full-duplex موفق بوده است؛ 10M، Half-duplex، زمان‌بندی Reset و بازیابی پس از Fault هنوز به پذیرش سخت‌افزاری نیاز دارند. Offload سخت‌افزاری Checksum، PTP، Wake-on-LAN و VLAN/Jumbo frame در این نسخه وجود ندارند.

### آزمون Throughput TCP

نمونه hal_eth_bench، شبکه embassy-net را روی همین درایور و با آدرس ثابت اجرا می‌کند: برد 192.168.47.1/24، پورت TCP شماره 5001 و پیکربندی PLL با فرکانس 200 MHz. رابط سیمی میزبان را در همین Subnet قرار دهید و اسکریپت Python استاندارد را اجرا کنید. Peer خطوط UP <bytes> یا DOWN <bytes> می‌فرستد؛ برد Payload بالارونده را می‌شمارد و دور می‌ریزد یا Payload پایین‌رونده تولید می‌کند و پاسخ OK <bytes> می‌دهد.

در 2026-11-04، سه دور انتقال 8 MiB روی 100BASE-TX، میانه Throughput برابر 94.12 Mbit/s برای Uplink و 91.95 Mbit/s برای Downlink اندازه‌گیری شد؛ نرخ Payload خط تقریباً 94.9 Mbit/s است. ETH_BENCH_RESULT در Init برابر 1، در حالت Listening برابر 2، پس از اتصال 3، پس از نشست Uplink برابر 4، پس از Downlink برابر 5 و در خطای Init برابر 10 است. ETH_BENCH_BYTES تعداد تجمعی بایت‌های Uplink و Downlink و ETH_BENCH_PHY_ID شناسه PHY را نگه می‌دارد.

### Throughput فریم خام

نمونه eth_raw_bench پایین‌تر از IP کار می‌کند: اسکریپت eth_raw_bench.py از طریق سوکت BPF در macOS و فریم‌های EtherType برابر 0x88b5 آدرس‌دهی‌شده به 02:00:00:00:00:48 با برد ارتباط برقرار می‌کند؛ بنابراین Routing یا پیکربندی آدرس میزبان لازم نیست.

فریم‌های کنترلی 60 بایتی با ساختار dst|src|88b5|cmd|count_le32|padding هستند. Peer فرمان D به‌همراه Count می‌فرستد تا برد همان تعداد فریم 1514 بایتی ارسال کند؛ فرمان U به‌همراه Count فریم‌های داده دریافتی را می‌شمارد و فرمان P پاسخ فوری می‌خواهد. گزینه rate سرعت نوشتن Uplink و batch تعداد فریم‌های ارسالی در هر Burst نوشتن را تنظیم می‌کند.

در 2026-11-04، انتقال 8192 فریم 1514 بایتی روی 100BASE-TX، میانه Downlink برابر 92.5 Mbit/s بدون فریم ازدست‌رفته و میانه Uplink برابر 82.3 Mbit/s با 6 تا 8 درصد فریم ازدست‌رفته را ثبت کرد. افت Uplink در سمت میزبان است: با batch 1 به 2 تا 3 درصد کاهش می‌یابد؛ زیرا مبدل USB RTL8156 نمی‌تواند Burst ارسال 100 Mbit/s را جذب کند. RAW_RESULT هنگام Init برابر 1، پس از Ping تأییدشده 2، پس از درخواست Uplink برابر 4، پس از دور Downlink برابر 5، در خطای Init برابر 10 و هنگام قطع Link برابر 12 است.

این Benchmark اشکال تو‌در‌تویی وقفه را آشکار کرد. وقتی Time-driver اولویت پایین‌تری از وقفه Ethernet دارد، کنترلر آن را Preempt می‌کند؛ فقط یک سطح Nesting مجاز است. ISR سطح دوم با mstatus.MIE خاموش اجرا می‌شود، Critical-section در qingke مقدار MPIE را بدون بازیابی پاک می‌کرد و mret با وقفه‌های غیرفعال بازمی‌گشت؛ در نتیجه Executor از حلقه wfi خارج نمی‌شد. نشانه آن بردی بود که پاسخی نمی‌داد، در حالی که SysTick و ETH در PFIC.IPR Pending و PFIC.IACTR پاک بودند. qingke نسخه 0.8.4 مقدار MPIE را بازیابی می‌کند؛ HAL نیز SysTick را در اولویت P0 پیش‌فرض Reset نگه می‌دارد تا پیکربندی پیش‌فرض هرگز Nesting نداشته باشد.

## اعتبارسنجی I3C در HAL

نمونه hal_i3c از کنترلر مستقل I3C در V4x7 استفاده می‌کند. پایه‌های پیش‌فرض SCL/SDA برابر PB10/PB11 هستند؛ Feature با نام i3c-remap پایه‌های PB4/PB5 را انتخاب می‌کند (پیش از استفاده، مالکیت پایه‌های Debug را بررسی کنید).

برنامه پیش‌فرض Readback رجیسترهای Timing/Control، آدرس کنترلر، مقداردهی اولیه مجدد، Mask وقفه‌ها و Clock gating هنگام Drop را بررسی می‌کند. مقادیر خام Timing، Fixture رجیستر هستند و پروفایل ارتباطی تأییدشده محسوب نمی‌شوند. این برنامه START یا CCC صادر نمی‌کند و I3C_RESULT=PASS فقط بررسی رجیستر و چرخه عمر را گزارش می‌دهد.

برای هدف واقعی I3C، ابتدا Timing را برای HCLK، هدف و Bus واقعی بررسی کنید. متغیرهای محیط ساخت I3C_TIMINGR0 و I3C_TIMINGR1 را با مقادیر خام رجیستر بازبینی‌شده (ده‌دهی یا Hex با پیشوند 0x) تنظیم و Feature با نام i3c-daa را اجرا کنید. عمداً هیچ پروفایل Timing ارتباطی پیش‌فرضی وجود ندارد. نبود متغیرها باعث شکست آزمون دستگاه پیش از ساخت کنترلر می‌شود. TIMINGR2 صفر است و Stall اختیاری ندارد. زمین مشترک، SCL و SDA را به یک هدف Native I3C متصل و آرایش Pull-up تعیین‌شده توسط هدف/برد را رعایت کنید. هدف صرفاً I2C نمی‌تواند ENTDAA را آزمایش کند.

آزمون دستگاه اختیاری RSTDAA را Broadcast می‌کند، آدرس‌های 0x30 تا 0x33 را به حداکثر چهار هدف اختصاص می‌دهد، PID/BCR/DCR را ثبت می‌کند و PID هر هدف را با GETPID مستقیم بررسی می‌کند. RSTDAA آدرس‌های Dynamic تمام اهداف I3C روی Bus را تغییر می‌دهد؛ بنابراین Bus آزمایشی اختصاصی و بدون کنترلر فعال دیگر آماده کنید. Markerهای Debugger شامل I3C_DEVICE_RESULT (صفر اجرا نشده، 1 شروع، 2 موفق)، I3C_TARGET_COUNT و I3C_TARGETS هستند. عملیات ناموفق در حال حاضر با خطای درایور Panic می‌کند؛ موفقیت Device از موفقیت آزمون رجیستر جداست.

Backend از Transferهای FIFO به‌صورت Blocking و Embassy، I2C قدیمی تک‌جهته از طریق Traitهای embedded-hal، Transferهای خصوصی SDR، CCCهای Broadcast/Direct معمول و ENTDAA پشتیبانی می‌کند. بخش RM §19.4.1 صراحتاً MEND=1 را برای پیام‌های Legacy I2C لازم می‌داند. تراکنش‌های Legacy که جهت را تغییر می‌دهند، از جمله write_read، پیش از فعالیت Bus با UnsupportedTransaction رد می‌شوند؛ آن‌ها به تراکنش‌های جداشده با STOP تبدیل نمی‌شوند. عملیات مجاور در یک جهت ادغام می‌شوند. Repeated START برای Transfer خصوصی و Direct CCC پشتیبانی می‌شود. عملیات I2C یا Private با طول صفر رد می‌شوند؛ Broadcast CCC با طول صفر پشتیبانی می‌شود. Direct CCC در حال حاضر Payload غیرخالی و بدون Defining byte می‌خواهد. RSTACT، تحویل IBI/hot-join و بازیابی خودکار فیزیکی Bus پیاده‌سازی نشده‌اند.

با Feature مربوط به i3c-dma، سازنده I3c::new_with_dma کانال DMA1_CH4 برای TX و DMA1_CH5 برای RX را در اختیار می‌گیرد. تراکنش‌های Private و Legacy پشتیبانی‌شده با حداکثر یک Buffer در هر جهت از DMA بایتی استفاده می‌کنند. تراکنش‌های پراکنده، CCC و ENTDAA همچنان از Backend مبتنی بر FIFO استفاده می‌کنند. هر دو کانال داده پیش از صف‌شدن کلمات کنترل مسلح می‌شوند؛ موفقیت نیازمند صفر بودن شمارنده‌های باقی‌مانده DMA و FCF است و خطاهای Peripheral/DMA اولویت دارند. نمونه عادی i3c-dma همچنان فقط بررسی رجیستر/چرخه عمر را انجام می‌دهد.

برای آزمون واقعی مسیر داده، یک Fixture بازتاب‌دهنده (Echo) از نوع Native I3C آماده کنید که RSTDAA/ENTDAA/GETPID را پشتیبانی کند و نوشتن Private قبلی را در خواندن Private بعدی بازگرداند؛ از جمله Repeated START بین نوشتن و خواندن. Fixture باید Payloadهای 1/7/8/9/31/257 بایتی را پشتیبانی کند. با I3C_TIMINGR0 و I3C_TIMINGR1 بازبینی‌شده، آزمون اختیاری i3c-dma-loopback را اجرا کنید. این آزمون Payload دلخواه را روی نخستین هدف تخصیص‌یافته می‌نویسد؛ از Fixture Echo اختصاصی استفاده کنید، نه Sensor یا دستگاه کاربردی دیگر. I3C_DMA_RESULT=2 نشان می‌دهد بررسی‌های نوشتن/خواندن جداگانه و Echo با Repeated-start موفق بوده و هر دو کانال و درخواست DMA پس از آن متوقف شده‌اند.

Backend مبتنی بر FIFO فقط FIFOهای داده هشت‌بایتی دارد. نه مدل میزبان و نه Build موفق، سرعت پایدار Bus یا تأخیر وقفه را اثبات نمی‌کند. DMA نیز پیش از ادعای پشتیبانی SDR پرسرعت، باید با Logic Analyzer و بار وقفه نماینده اعتبارسنجی شود. Legacy I2C سازگاری Clock-stretching را تضمین نمی‌کند. فریم‌های ناموفق/لغوشده پس از بازگرداندن Bus فیزیکی به حالت Idle، به reinitialize() صریح نیاز دارند؛ این متد هدف گیرکرده را پاک نمی‌کند یا آدرس Dynamic آن را Reset نمی‌کند. خروجی ENTDAA در خطا، از جمله پرشدن ظرفیت، موقت است. آدرس‌های ارائه‌شده باید روی Bus موجود آزاد باشند؛ درایور فقط Reservationها، موارد تکراری و آدرس خودش را بررسی می‌کند.

بررسی رجیستر/چرخه عمر در 2026-11-03 روی سخت‌افزار موفق شد. هنوز هیچ هدف خارجی I3C یا Fixture مربوط به Echo با DMA آزمایش نشده است.

# CH32V467 first bring-up

The original examples are **PAC-only**. `hal_init` additionally exercises the
initial HAL support: HSI clocks, bus dividers, GPIO clock/reset setup and optional
Embassy driver initialization. Peripheral drivers are still being migrated.
The HAL and examples use the same pinned Git PAC revision, `e150d53`, generated
from ch32-data `844640b` (#78). Firmware builds do not require sibling PAC or
qingke checkouts; qingke/qingke-rt are resolved from crates.io.

## Build

Run from this directory with a recent Rust toolchain:

```sh
rustup target add riscv32imc-unknown-none-elf
cargo build --release --bins
```

The default part is **CH32V467WEU6**, with the board LED on **PE8/PE9**.
Select exactly one part for another package:

```sh
cargo build --release --bins --no-default-features --features ch32v467ret6
cargo build --release --bins --no-default-features --features ch32v467vet6
```

### HAL stages 0–1

The Git PAC revision is fixed in both Cargo manifests until the corrected
V4x7 metadata is released. HAL dependencies require qingke/qingke-rt 0.8.4
or newer for V3V (0.8.4 is the first release with the `mstatus.MPIE`
critical-section fix).

```sh
cargo run --release --bin hal_init --features hal
cargo run --release --bin hal_init --features hal,clock-dividers
cargo run --release --bin hal_init --features embassy
```

`hal_init` calls `ch32_hal::init()` once, checks the RCC clock cache, HSI status,
GPIO/AFIO clock enables and `rcc::refresh(None)`, then reports
`HAL_INIT_RESULT=PASS` over RTT and repeats a heartbeat. With `clock-dividers`,
SYSCLK/HCLK/PCLK1/PCLK2 are 20/10/2.5/5 MHz; otherwise all four are 20 MHz.
It has no GPIO outputs. `HAL_INIT_RESULT` is 0 before entry, 1 while checking,
2 on success, or 3 on a failed check.

The blocking variant uses the HAL SysTick delay. With `embassy`, it instead
checks SysTick configuration and uses a CPU spin loop for the heartbeat;
executor, Timer accuracy, rollover and sleep/wake validation belong to stage 3.
Do not use the blocking `Delay` while Embassy owns SysTick.

HAL defaults are disabled here; opt into GPIO EXTI with `exti`. TIM-based time
drivers still reject V4x7 until ported. DMA and other unported drivers are not exposed. HSE/PLL
configuration is not available, and `refresh` rejects those clock sources.

### HAL stage 2: GPIO and EXTI

Build locally without programming the board:

```sh
cargo build --release --bin hal_blinky --features hal
cargo build --release --bin hal_exti --features exti
```

`hal_blinky` alternates PE8 and PE9 through HAL GPIO outputs, using a nominal
100 ms blocking delay. It checks both output latch and pad readback after each
transition and reports `GPIO_OUT_RESULT=PASS` after 20 transitions. The debugger
symbol is 0 before entry, 1 while running, 2 on success, and 3 on failure. With
`embassy`, it uses a CPU spin loop; executor-based blinking uses `hal_embassy`.
Output readback passed on WEU6, and the PE8/PE9 LED alternation was confirmed
visually on 2026-11-04; waveform accuracy still requires an instrument.

For `hal_exti`, connect **PA0 to PB1, PB8 and PC13** as one signal net (three
jumper branches). Check that these pins are exposed and free of external drivers
on your board before running. The program initially floats PA0 and tests each
input's pull-up/down individually, restoring floating mode between tests. It
then drives PA0 and waits on all three inputs concurrently, covering EXTI1,
EXTI9_5 and EXTI15_10 and GPIO B/C routing. Eight rounds check rising/falling/any
edges, actual IRQ wake callbacks, future cancellation, stale pending clearance
and rearming. Each edge wait has a bounded polling timeout.

This example polls futures directly and does not use an executor or Timer. It
reports `GPIO_EXTI_RESULT=PASS` over RTT; the debugger symbol is 0 before entry,
1 while running, 2 on success, and 3 on a failed check. Failures halt. A missing
jumper can also fail the earlier pull/routing checks. Hardware acceptance is
pending; building does not verify electrical behavior or interrupt delivery.

After preparing the wiring, these commands program and run the examples:

```sh
cargo run --release --bin hal_blinky --features hal
cargo run --release --bin hal_exti --features exti
```

USART1's split remap fields (PCFR1 bit 2 and PCFR2 bit 26) are implemented and
covered by local register-model checks. USART transfers remain a later stage.

### HAL stage 3: Embassy

```sh
cargo build --release --bin hal_embassy --features embassy
cargo run --release --bin hal_embassy --features embassy
cargo run --release --bin hal_embassy --features embassy,clock-dividers
```

No input wiring is needed. The example owns SysTick, places its 32-bit counter
near rollover before application timers exist, checks monotonic time, then runs
three tasks with 100/150/230 ms timers for 16 iterations each. Two tasks drive
PE8/PE9. It checks alarms across rollover, cancelled and past deadlines, short
deadlines, and eight WFI waits with interrupts masked. RTT reports
`EMBASSY_RESULT=PASS`, followed by a continuous timer-based heartbeat. The result
symbol uses 0/1/2/3 for not entered/running/pass/fail. The rollover setup is
test-only; applications must not reset or rewrite the running time counter.

V4x7 has a **32-bit CNT and 32-bit CMP**, with reserved words at 0x0c and 0x14.
The pinned PAC no longer exposes invented high-word or 64-bit views. A dedicated
driver extends the counter in software and keeps maintenance interrupts active
even without user timers. Interrupts must not remain masked for half a wrap
(about 859 seconds at the default clock). Time conversion supports the
noninteger counter/tick ratios at HCLK=20 MHz and 10 MHz.

Both clock configurations passed on WEU6 on 2026-11-01, including IRQ wakeup and
WFI. Host-observed RTT heartbeat intervals were approximately one second;
calibrated oscillator accuracy and sleep current were not measured. GPIO input
and external EXTI validation remain deferred until wiring is available.

The stock RV32IMC target is extended in `.cargo/config.toml` with
`-C target-feature=+xwchc,+zve64x,+zvl64b,+zvbb`. It retains the soft-float
ILP32 ABI and does not enable native CAS. These vector features match WCH's
`EVT/EXAM/CPU/AccuracyDelayInTick/AccuracyDelayInTick.wvproj` in the
[CH32V407/CH32V467 SDK](https://github.com/openwch/ch32v407_ch32v467).
Use the embedded integer vector subset rather than `+v`, which also implies
floating-point vector capabilities and a minimum VLEN of 128 bits. This board
reports VLEN = 64 bits and no scalar F extension.

The current rustc nightly (1.101.0-nightly, 2026-10-17, LLVM 23.1.4) warns that
`xwchc` is an unknown/unstable Rust target feature, but passes it to LLVM.
The ELF architecture attribute includes `xwchc2p2`, and disassembly and the
board test below confirm that it is effective. A future rustc may reject this
flag; keep this toolchain available when reproducing the test. `xwchc` is not
exposed through Rust's `cfg(target_feature)`, so the ISA example checks vector
features at compile time and tests WCH compressed instructions at runtime.

qingke-rt 0.8.4 from crates.io provides V3V core startup via `qingke-rt/v3v`,
and the PAC provides the device vectors and memory layout.
No custom linker memory map is maintained.
The PAC's default `c512_r200` split is 512 KiB primary flash + 200 KiB SRAM;
another 480 KiB flash follows it. The generated linker script merges the flash
regions into a 992 KiB boot alias at `0x00000000`; the stack top is `0x20032000`.
The chip option-byte split must match. Do not change option bytes blindly.

## Examples and observation

- `blinky`: the board LEDs on PE8/PE9 alternate every nominal 100 ms (5 Hz
  per LED). Logs clock setup and each heartbeat over **defmt RTT**, not SDI.
  PE8/PE9 are 2 MHz push-pull outputs driven at opposite levels.
- `rtt`: no GPIO outputs; logs before clock init and repeats clock/heartbeat
  information every nominal second. Replaces the former `sdi_print` example.
- `cpuid`: no GPIO outputs; prints a one-shot CPU identity report over defmt
  RTT after a 500 ms attachment window, following the CH585 example's output
  style. Includes `mvendorid`, `marchid`, `mimpid`, `mhartid`, `misa`, raw
  hexadecimal values, CSR presence, WCH-style identity fields, XLEN and ISA
  extension bits (including F/V). Illegal CSR reads during a probe report
  `present=false`; unrelated exceptions halt. Zero is not treated as absent.
  Decoded fields do not identify the package, and advertised ISA bits do not
  prove instruction behavior or safe atomics. The example only reads CSRs;
  `qingke-rt/v3v` enables vector state (mstatus.VS = Dirty) during startup.
  The report is not repeated; re-run/reset for another report.
- `isa`: tests WCH compressed byte/halfword loads and stores, plus separate
  Rust volatile-copy functions for disassembly. Tests `vsetvli`, vector loads,
  `vadd.vv`, stores and Zvbb `vror.vi` with 8/16/32/64-bit elements. Each case
  processes 19 elements in variable-length chunks and compares every result
  against scalar wrapping addition and rotation, including overflow and tails.
  Logs failures and synchronous traps over RTT. `ISA_RESULT` is 0 before the
  test, 1 while running, 2 for PASS, or 3 for failure/trap. No GPIO outputs.
- All expose ELF symbols `BOOT_STAGE` (1 = entered init, 2 = clock/SysTick
  configured) and `HEARTBEAT` for debugger inspection without a console.

`defmt.x` retains the log metadata, `defmt-rtt` provides `_SEGGER_RTT` in RAM,
and `qingke/critical-section-impl` serializes the single-core logger. RTT does
not depend on the SDI DATA0/DATA1 addresses. `disable-blocking-mode` keeps
execution moving if the host disconnects; a full buffer can lose log data.
The panic handler is still `panic-halt`: Rust panics halt without panic text.

## USBHS device / CDC echo

```sh
cargo run --release --bin hal_usbhs --features usbhs
cargo run --release --bin hal_usbhs --features usbhs,clock-pll
cargo run --release --bin hal_usbhs --features usbhs,clock-hse
cargo run --release --bin hal_usbhs --features usbhs2
python3 usbhs_echo_test.py /dev/ttyACM0                    # Linux
python3 usbhs_echo_test.py /dev/tty.usbmodemV4_USBHS11     # macOS, USBHS1
```

The default uses USBHS1: PA12 = D+, PA11 = D−. `usbhs2` selects USBHS2:
PB7 = D+, PB6 = D−, available on VET6/WEU6, not RET6. Connect the matching
USB data connector and a common ground. The WCH-Link debug connection does not
provide a USB host connection to these pins. Do not use both instances on the
same pair of wires. USBHS2 uses its own interrupt, bus gate and UTMI gate.

The example uses **full-speed USB** with 64-byte CDC bulk packets. HSI feeds the
shared 480 MHz USBHS PLL; `clock-pll` additionally runs HCLK at 200 MHz.
`clock-hse` requires a 25 MHz crystal and instead supplies the USBHS PLL from HSE.
HSI operation has now passed enumeration and echo; long-run stability and
frequency accuracy still need testing. Use the actual board crystal
configuration when assessing USB frequency accuracy.
The demonstration VID/PID is `c0de:cafe`, matching the existing USB examples;
it is not a production allocation.

Open the enumerated CDC port with DTR asserted. The Linux test script has no
third-party dependencies and checks binary payloads spanning 1–4096 bytes,
including 63/64/65-byte boundaries and all byte values. It transfers both ways
concurrently and fails on mismatches, disconnects or timeout. Expect
`PASS: 120 exchanges, 62160 bytes matched` with the default ten rounds.
The firmware adds an IN ZLP after a full 64-byte packet so exact packet-sized
echoes are delivered without waiting for another packet.

On 2026-11-04, USBHS1 enumerated and echoed on a macOS host
(`/dev/tty.usbmodemV4_USBHS11`); the default ten-round test reported
`PASS: 120 exchanges, 62160 bytes matched`. USBHS2, the PLL/HSE clock variants,
bus reset, cable reconnect and high-speed operation remain untested on hardware.

Debugger symbols: `USBHS_STAGE` = 1 initializing, 2 waiting for CDC connection,
3 connected, 4 echoed data. `USBHS_ECHO_PACKETS`, `USBHS_ECHO_BYTES` and
`USBHS_ERRORS` record successful packets/bytes and buffer overflow errors.
Stage 4 alone is not a complete pass: compare host data, exercise bus reset,
close/reopen and reconnect, and check that the error counter remains zero.

The driver borrows aligned internal SRAM for the bus/endpoint lifetimes. EP0
reserves 64 bytes; each non-control direction allocates its own packet buffer.
Physical endpoints 1–7 are exposed; paired IN/OUT directions must have equal
maximum packet sizes because hardware shares the length register. Canceling
an IN write may leave its owned packet queued; the next write waits for that
packet before copying new data. Reset, disable and new control SETUP invalidate
pending transfers. The driver does not detect VBUS removal; physical cable
removal cannot currently produce a `PowerRemoved` event.

This CDC example intentionally uses full speed. High-speed PHY, isochronous
timing, remote wakeup and full-speed fallback need hardware tests. Embassy USB
0.6 does not supply an other-speed configuration descriptor, so switching only
the driver's speed is insufficient for a complete dual-speed device. Endpoint
aliases 9–15, burst mode, LPM and USB host mode remain pending.

A host register model covered packet allocation during development (27 checks);
it has since been removed in favour of this on-board example. The 16-case
library matrix and six CDC example build configurations passed, and USBHS1
enumeration and CDC echo passed on the board on 2026-11-04; the remaining
hardware items are listed above.

## SysTick rollover stress test (2026-11-01)

```sh
cargo run --release --bin hal_systick_stress --features embassy
cargo run --release --bin hal_systick_stress --features embassy,clock-dividers
cargo run --release --bin hal_systick_stress --features embassy,clock-pll,stress-natural-wrap
```

This test uses TIM2 as a reference counter and watchdog; it requires no input
wiring. Each run exercises 512 accelerated SysTick rollovers, alternating normal
interrupt handling with 50/500/2000 us of masked interrupts across the boundary.
It checks that the ISR rearms CMP before allowing the foreground to read Embassy
time again, so foreground reads cannot hide a missed rollover. It also checks the
software epoch, deadlines and a two-second relative time measurement.

Three standalone runs per clock configuration passed all 3072 rollovers. Measured
3 ms waits were 3036–3098 us at HCLK 20 MHz and 3076–3152 us at HCLK 10 MHz.
These include ISR/executor latency and are observed samples, not worst-case bounds.
TIM2 and SysTick share HSI, so this does not calibrate oscillator accuracy. A
natural 32-bit wrap and very long interrupt masking remain separate tests.
`clock-pll,stress-natural-wrap` adds a complete natural counter period at
HCLK = 200 MHz (about 172 seconds), after the accelerated tests. During that
period, foreground code uses TIM2 and waits for the SysTick ISR to rearm CMP
before polling the Embassy timer or reading Embassy time again. This additional
test has been built but has not yet passed on hardware.

For a negative control, add `stress-disable-systick-irq`: the watchdog must report
`FAIL code=13`. Reflash a normal configuration afterward. With no continuous RTT
connection, inspect `SYSTICK_STRESS_RESULT` (1 running, 2 passed, 10–18 failed) and
`SYSTICK_STRESS_STATS` (rounds, min/max wait, TIM2 elapsed, Embassy elapsed; us).
Allow five seconds after reset before attaching to read the result. Continuous
debugger access can introduce much larger latency or lose short TIM2 reference
periods; the reference uses the full 65.536 ms counter period to reduce this risk.

`hal_time_scale --features embassy` checks the conversion of stopped hardware
counter values against a wide integer reference. Add `clock-pll` for 200 MHz
HCLK or `clock-slow` for AHB /512. The latter has a fractional SysTick frequency;
the driver preserves the source/divider ratio instead of truncating it to Hz.
The example restores HSI /1 after checking, allowing the debugger to reconnect.
After the 2026-11-03 recovery, the default, PLL and AHB/512 configurations
passed on hardware, as did `hal_systick_stress` with the default and divided
clocks (512 rollovers each) and the `stress-disable-systick-irq` negative
control (`FAIL code=13`). The `stress-natural-wrap` variant (about 172 seconds)
has not been run yet.

During the earlier slow test, HCLK stayed at about 39 kHz and the probe could
not attach. The version that restores HSI /1 was flashed after a power-off
erase, and the board has been recovered as described above.

## DMA migration check (2026-11-01)

```sh
cargo build --release --bin hal_dma --features embassy
cargo run --release --bin hal_dma --features embassy
```

The example tests all 13 DMA1 and 11 DMA2 channels, including both register
windows. It performs 216 copies across byte/halfword/word widths, checks byte
lengths 1/2/3/31/256/65535 and buffer guards, then cancels a transfer without a
peripheral request and reuses that channel. Each copy has a two-second timeout.
No signal wiring is needed. The large buffers use about 133 kB of RAM; retain

## Flash migration check (2026-11-01)

```sh
cargo run --release --bin hal_flash --features hal
```

The default example only reads Flash and checks invalid ranges and empty requests.
It records `FLASH_RESULT` (1 running, 2 pass, 10–28 failure), `FLASH_SNAPSHOTS`,
`FLASH_TEST_RANGE` and `FLASH_TEST_CASES`. No erase or program command is issued.

For an explicitly destructive storage test:

```sh
cargo run --release --bin hal_flash --features hal,flash-write-test
cargo run --release --bin hal_flash --features embassy,flash-write-test,clock-pll
```

`flash-write-test` erases existing contents of the final 32 KiB,
`0x080F0000..0x080F8000`. It enables `memory-split-usr` and reserves that region
with `flash-test.x`; the ELF contains a NOLOAD reservation with no download bytes.
Code remains in zero-wait Flash. Custom applications must also ensure erase/program
functions and their callees execute from zero-wait Flash, as required by the RM.

V4x7 supports 256-byte fast programming, 16-bit standard programming, 4 KiB sector
erase and 32 KiB fast block erase. Raw erased halfwords read as `0xE339`.
The raw driver therefore implements `ReadNorFlash` only. `into_nor_flash(from, to)`
creates an explicit data partition whose XOR encoding normalizes erased bytes to
`0xFF`, allowing the `NorFlash` contract. This representation changes stored bytes
and is unsuitable for firmware images. Erase before reprogramming; the driver does
not provide multiple-write guarantees or track physical programming history.

The optional test checks both erase sizes, both programming modes, unaligned source
buffers, readback verification, repeated-program rejection and the encoded partition.
It checks protection and clock snapshots without changing option bytes, protection
or RAM/code allocation. Interrupts are masked during each physical operation;
the datasheet allows up to 200 ms for a block erase. A busy timeout leaves controller
registers untouched: retain the driver and retry `recover()` once hardware is idle.
`Config::poll_limit` counts register polls, not elapsed time.

The combined host suite passes 104 tests, and the 16-configuration library matrix
passes. Read-only, write-test and Embassy/200 MHz PLL builds link successfully.
ELF inspection confirms the reserved range and zero-wait operation entrypoints.
Read-only and `flash-write-test` flows passed on hardware on 2026-11-03, after
fixing the fast-page busy wait (it waited for `BSY|WRBSY` instead of `WRBSY`).
Endurance and worst-case erase timing remain untested.

## CAN migration check (2026-11-01)

```sh
cargo run --release --bin hal_can --features embassy
cargo run --release --bin hal_can --features embassy,clock-pll,clock-dividers
```

The example uses CAN1 SilentLoopback on PA11/PA12, so no transceiver or wiring is
needed. It first checks blocking loopback at 125/500/1000 kbit/s, then 72 standard
and extended data/remote frames with payload lengths 0–8. Exact filters route
standard frames to FIFO0 and extended frames to FIFO1 through banks 0 and 13.
It also checks rejected identifiers, invalid filter banks, canceled pending
receives, reuse, FIFO overrun reporting and clock release when the driver drops.

`CAN_RESULT` is 1 while running, 2 on success and 10–26 on failure.
`CAN_FRAMES` counts standard data, extended data, standard remote and extended
remote frames. `CAN_SNAPSHOTS` contains PCLK1, BTIMR, filter activation, filter
FIFO assignment, interrupt enables and error status.

The dedicated V4x7 API supports both receive FIFOs, all 14 filter banks and
16/32-bit list/mask filters. `Filter::exact` matches ID format and optionally RTR;
raw `Filter::registers` exposes the RM filter representation for other layouts.
Bitrate selection requires an exact clock ratio and uses all ten prescaler bits.
Standard TS1/TS2/SJW ranges follow EVT; extended long-TS1, time-triggered mode and
CAN FD are not enabled. This chip implements Classical CAN 2.0A/B.

Both blocking and async transmission wait for a completion result. Nonblocking
`try_transmit` only submits a frame and returns a mailbox; its result is valid
until that mailbox is reused or the controller is dropped. Pending frames are
never replaced. The embedded-can blocking/nb traits receive from FIFO0; explicit
receive methods select either FIFO. Wrap async operations in `with_timeout` as
needed. Blocking `Config::poll_limit` counts register polls rather than time.
Canceling transmit requests abort only for the future's own mailbox; it cannot
withdraw a frame already sent on the bus. Receive cancellation disables its
interrupt sources. An overrun reports loss while leaving queued frames readable.

The combined host suite passes 128 tests, including CAN frame/timing/filter and
controller lifecycle/interrupt/cancellation checks. All 16 library configurations
pass, and both example configurations build and link. The 72-frame internal
loopback passed on hardware on 2026-11-03. Real bus timing, arbitration,
transceivers and electrical quality still need an external CAN setup.

### Raw-frame throughput

`eth_raw_bench` stays below IP: `eth_raw_bench.py` drives it through a macOS BPF
socket with EtherType 0x88b5 frames addressed to `02:00:00:00:00:48`, so no host
routing or address configuration is involved.

```sh
cargo run --release --bin eth_raw_bench --features eth
sudo python3 eth_raw_bench.py en9
```

Control frames are 60 bytes `dst|src|88b5|cmd|count_le32|padding`. The peer
sends `D` + count to make the board transmit that many 1514-byte frames, `U` +
count to count incoming data frames, and `P` for an immediate acknowledgement.
`--rate` paces the uplink writes and `--batch` sets how many frames go out per
write burst.

On 2026-11-04, 8192 x 1514-byte frames over 100BASE-TX measured 92.5 Mbit/s
median downlink with no missing frames, and 82.3 Mbit/s median uplink with 6-8%
of frames missing. The uplink loss is on the host side: it drops to 2-3% with
`--batch 1`, because the RTL8156 USB adapter cannot absorb a 100 Mbit/s transmit
burst. `RAW_RESULT` is 1 during init, 2 for an acknowledged ping, 4 after an
uplink request, 5 after a downlink round, 10 on init failure and 12 while the
link is down.

Running this benchmark exposed an interrupt-nesting bug. With the time driver
at a lower priority than the Ethernet interrupt the controller preempts, and
only one nesting level is allowed: a second-level ISR runs with `mstatus.MIE`
clear, the `qingke` critical section cleared `MPIE` without restoring it, and
`mret` returned with interrupts disabled, so the executor never left its `wfi`
loop. The symptom was a board that answered nothing while SysTick and ETH
stayed pending in `PFIC.IPR` with `PFIC.IACTR` clear. `qingke` 0.8.4 restores
`MPIE`; the HAL also keeps SysTick at the reset P0 priority so the default
configuration never nests.

are register fixtures, not a qualified communication profile. It issues no START
or CCC, and `I3C_RESULT=PASS` only reports those register/lifecycle checks.

For a real I3C target, first review timings for the actual HCLK, target and bus.
Set the build environment variables `I3C_TIMINGR0` and `I3C_TIMINGR1` to the
reviewed raw register values (decimal or `0x` hex), then run:

```sh
cargo run --release --bin hal_i3c --features embassy,i3c-daa
```

There is deliberately no default communication timing profile. Missing variables
cause the device test to fail before controller construction. TIMINGR2 is zero
(no optional stalls). Wire common ground, SCL and SDA to a native I3C target and
use the pull-up arrangement specified by the target/board. An I2C-only target
cannot exercise ENTDAA.

The opt-in device test broadcasts RSTDAA, assigns 0x30–0x33 to at most four
targets, records PID/BCR/DCR, and checks each PID using direct GETPID. RSTDAA
changes all I3C target dynamic addresses on that bus. Prepare a dedicated test
bus with no other active controller. Debugger markers are `I3C_DEVICE_RESULT`
(0 not run, 1 started, 2 passed), `I3C_TARGET_COUNT` and `I3C_TARGETS`.
Failed operations currently panic with the driver error; a device PASS is
separate from the register PASS.

The backend supports blocking and Embassy FIFO transfers, single-direction legacy
I2C via both embedded-hal traits, SDR private transfers, ordinary broadcast/direct
CCC and ENTDAA. RM §19.4.1 explicitly requires MEND=1 for legacy I2C messages.
Legacy transactions changing direction, including write_read, return
`UnsupportedTransaction` before bus activity; they are not split into separate
STOP-delimited transactions. Adjacent operations in one direction are merged.
Repeated starts are supported for private transfers and direct CCC.
Zero-length I2C or
private operations are rejected; zero-length broadcast CCC is supported. Direct
CCC currently requires a nonempty payload and no defining byte. RSTACT,
IBI/hot-join delivery and automatic physical bus recovery are not implemented.

With `i3c-dma`, `I3c::new_with_dma` owns DMA1_CH4 for TX and DMA1_CH5 for RX.
Private and supported legacy transactions with at most one buffer per direction
use byte DMA. Scattered transactions, CCC and ENTDAA retain the FIFO backend.
Both data channels are armed before control words are queued; success requires
zero remaining DMA counts and FCF, with peripheral/DMA errors taking priority.
The normal `i3c-dma` example still performs only register/lifecycle checks.

For an actual data-path test, prepare a native I3C **echo fixture** that supports
RSTDAA/ENTDAA/GETPID and returns the previous private write on a subsequent private
read, including a repeated START between write and read. The fixture must handle
1/7/8/9/31/257-byte payloads. With reviewed `I3C_TIMINGR0` / `I3C_TIMINGR1`, run:

```sh
cargo run --release --bin hal_i3c --features embassy,i3c-dma-loopback
```

This opt-in test writes arbitrary payloads to the first assigned target. Use the
dedicated echo fixture rather than a sensor or other application device.
`I3C_DMA_RESULT=2` indicates that separate write/read and repeated-start echo
checks passed and that both DMA channels and requests stopped afterward.
Communication failure returns the driver error. Neither successful echo nor
the host model establishes a maximum bus speed. Measure SCL/SDA and exercise
representative interrupt load before qualifying a timing profile.

The FIFO backend has only eight-byte data FIFOs. Neither the host model nor a
successful build establishes a sustainable bus speed or interrupt latency.
DMA also needs validation with a logic analyzer and representative interrupt
load before claiming high-rate SDR support. Legacy I2C does not promise
clock-stretching compatibility. Failed/cancelled frames require explicit
`reinitialize()` after restoring an idle physical bus; this method does not
clear a stuck target or reset its dynamic address. ENTDAA output is provisional
on error, including capacity exhaustion. Supplied addresses must be unused on
the existing bus; the driver only checks reservations, duplicates and its own
address.

The register/lifecycle check passed on hardware on 2026-11-03. No external
I3C target or DMA echo fixture has been tested yet.
